安全模型总览

OpenClaw 是一个多通道 AI 网关，连接 Telegram、Discord、Slack、Signal、WhatsApp 等多个消息平台。 每个通道都可能接收到来自不同用户的消息，这些消息可能触发 AI Agent 执行各种操作——包括运行系统命令。 因此，安全不是某一个模块的事，而是贯穿整个请求生命周期的多层防线。

安全层次：纵深防御
第 1 层：消息入口控制
DM Policy + Group Policy — 谁可以给 Bot 发消息？
消息被接受后
第 2 层：身份认证
Device Pairing — 设备/客户端配对 + Token 认证
Agent 需要执行命令时
第 3 层：执行审批
Exec Approvals — 命令必须经过人工批准
Agent 调用工具时
第 4 层：工具权限
Tool Policy — per-agent allow/deny 工具白名单
核心原则

默认安全（Secure by Default）：DM Policy 默认 pairing（需要配对才能对话），Group Policy 默认 allowlist（需要在白名单才能触发），Exec Approval 默认需要人工确认。

用户必须主动放宽安全限制，而不是被要求主动加固。

DM Policy 四模式

DM Policy 控制谁可以通过私信（Direct Message）与 Bot 对话。 每个通道（Telegram、Discord、Slack 等）独立配置，共有 4 种模式。

TypeScript src/config/types.base.ts — DmPolicy 类型定义 
export type DmPolicy = "pairing" | "allowlist" | "open" | "disabled";
DM Policy 四模式对比
pairing
默认
未知用户触发配对流程，审批后自动加入白名单
allowlist
严格
仅配置文件中明确列出的用户可以对话
open
开放
任何人都可以 DM Bot（需要 allowFrom 包含 "*"）
disabled
关闭
完全忽略所有 DM 消息

决策流程

TypeScript src/security/dm-policy-shared.ts — DM 访问决策 
export function resolveDmGroupAccessDecision(params) {
  const dmPolicy = params.dmPolicy ?? "pairing";  // 默认 pairing

  if (dmPolicy === "disabled") {
    return { decision: "block", reason: "dmPolicy=disabled" };
  }
  if (dmPolicy === "open") {
    return { decision: "allow", reason: "dmPolicy=open" };
  }
  if (params.isSenderAllowed(effectiveAllowFrom)) {
    return { decision: "allow", reason: "dmPolicy=... (allowlisted)" };
  }
  if (dmPolicy === "pairing") {
    return { decision: "pairing", reason: "dmPolicy=pairing (not allowlisted)" };
  }
  // allowlist 模式：不在名单中就拒绝
  return { decision: "block", reason: "dmPolicy=allowlist (not allowlisted)" };
}
Pairing 模式的精妙

pairing 模式是安全性和易用性的平衡点：未知用户发消息时不会被直接拒绝， 而是触发一个"配对请求"流程——操作者可以在控制面板或 Telegram 中看到请求并一键批准。 批准后，该用户会自动被加入白名单（pairing store），后续消息直接放行。

白名单来源合并

DM 的白名单不仅来自配置文件 (allowFrom)，还包括通过配对流程批准的用户（存储在 pairing store 文件中）。 两个来源会被合并成一个 effectiveAllowFrom 列表用于访问判定。

Group Policy

Group Policy 控制Bot 在群组/频道中如何响应消息。与 DM Policy 独立配置， 适用于 Telegram 群组、Discord 服务器频道、Slack 频道等场景。

TypeScript src/config/types.base.ts — GroupPolicy 类型定义 
export type GroupPolicy = "open" | "disabled" | "allowlist";
模式 默认 行为 适用场景
allowlist 是 仅在配置的群组/频道中响应，且仅响应白名单用户 生产环境，精确控制 Bot 活跃范围
open 否 在所有群组中响应所有用户 开发测试，或信任所有群组成员
disabled 否 完全忽略群组消息 仅允许 DM 交互的 Bot

每通道独立配置

每个通道可以有自己的 Group Policy。例如 Telegram 可以设为 allowlist（仅允许特定群组）， 而 Discord 设为 open（允许所有服务器）。全局默认值通过 channels.defaults.groupPolicy 配置。

对于 Telegram，群组访问控制还可以细化到每个群组甚至每个 Topic， 通过 channels.telegram.groups.<groupId> 进行精细配置。

DM vs Group 类比

DM Policy 相当于你家的门锁——决定谁能进你的房子。 Group Policy 相当于公司会议室的门禁卡——决定 Bot 可以进入哪些会议室，以及在会议室里听谁说话。 两者独立运作，互不影响。

Device Pairing 设备配对

Device Pairing 是 OpenClaw 的设备身份认证机制——允许移动 App、桌面客户端或第三方集成 安全地连接到 Gateway。配对流程遵循"请求 - 审批 - Token 生命周期"的三阶段模式。

配对流程

Device Pairing 三阶段流程
阶段 1：请求
设备发送 deviceId + publicKey + 元数据
请求被存入 pending 队列（5 分钟 TTL）
操作者审批
阶段 2：审批
操作者点击"批准"
生成 Token 并绑定角色/权限范围
设备持 Token 连接
阶段 3：Token 生命周期
创建 / 验证 / 轮换 / 撤销
基于角色 + 权限范围的细粒度控制

数据结构

TypeScript src/infra/device-pairing.ts — 核心类型 
type DevicePairingPendingRequest = {
  requestId: string;       // 请求唯一 ID
  deviceId: string;        // 设备标识
  publicKey: string;       // 设备公钥
  displayName?: string;    // 设备显示名（如 "iPhone 15"）
  platform?: string;       // 平台（如 "ios", "macos"）
  role?: string;           // 请求的角色
  scopes?: string[];       // 请求的权限范围
  ts: number;              // 请求时间戳
};

type PairedDevice = {
  deviceId: string;
  publicKey: string;
  roles?: string[];          // 已批准的角色列表
  approvedScopes?: string[]; // 已批准的权限范围
  tokens?: Record<string, DeviceAuthToken>;  // 每个角色一个 Token
  createdAtMs: number;
  approvedAtMs: number;
};

type DeviceAuthToken = {
  token: string;            // 认证令牌
  role: string;             // 绑定的角色
  scopes: string[];         // 权限范围
  createdAtMs: number;
  rotatedAtMs?: number;     // 最近一次轮换时间
  revokedAtMs?: number;     // 撤销时间（如有）
  lastUsedAtMs?: number;    // 最近使用时间
};

Token 生命周期操作

操作 函数 说明
请求配对 requestDevicePairing() 设备发起配对请求，存入 pending 队列（5 分钟过期）
批准配对 approveDevicePairing() 操作者批准请求，生成 Token 并转移到 paired 列表
拒绝配对 rejectDevicePairing() 操作者拒绝请求，从 pending 中删除
验证 Token verifyDeviceToken() 检查 Token 有效性、角色匹配、权限范围
轮换 Token rotateDeviceToken() 生成新 Token 替换旧 Token（保留元数据）
撤销 Token revokeDeviceToken() 标记 Token 为已撤销，不删除记录
移除设备 removePairedDevice() 完全删除设备配对记录
Scope 权限模型

每个 Token 绑定了一组 scopes（权限范围）。验证时不仅检查 Token 本身的合法性，还会检查请求的操作是否在 Token 的 scopes 范围内。

此外，Token 的 scopes 必须是设备 approvedScopes 的子集——即使 Token 被轮换，也不能获得超出初始批准范围的权限。

Exec Approvals 执行审批

当 AI Agent 需要执行系统命令（如运行 shell 命令、操作文件）时，Exec Approvals 机制 确保每个命令都必须经过人工审批或通过安全策略的自动放行。

安全策略三级

TypeScript src/infra/exec-approvals.ts — 安全级别 
export type ExecSecurity = "deny" | "allowlist" | "full";
export type ExecAsk = "off" | "on-miss" | "always";
ExecSecurity 行为 适用场景
deny 完全禁止 不允许 Agent 执行任何系统命令
allowlist 白名单控制 仅允许白名单中的命令；其他命令需要审批
full 完全允许 允许所有命令（但仍可配合 ask 进行审批）
ExecAsk 行为
off 不弹出审批请求（由 security 策略直接决定）
on-miss 命令不在白名单时，弹出审批请求
always 所有命令都弹出审批请求

双层审批架构

Exec Approvals 采用双层架构——Gateway 层和 Node 层各有独立的审批逻辑：

Gateway 层

ExecApprovalManager 管理审批的生命周期：创建请求、等待决定、超时处理。 审批请求通过 WebSocket 广播到所有连接的客户端（控制面板、Telegram Bot 等）。

src/gateway/exec-approval-manager.ts

Node 层

evaluateSystemRunPolicy() 在命令实际执行前进行最终决策： 综合 security、ask、白名单匹配和审批结果，决定是否放行。

审批决定类型

export type ExecApprovalDecision = "allow-once" | "allow-always" | "deny";

// allow-once  — 仅本次允许（一次性消费，不可重放）

// deny        — 拒绝执行

审批流程

TypeScript src/node-host/exec-policy.ts — 策略评估核心 
export function evaluateSystemRunPolicy(params) {
  // 1. security=deny → 直接拒绝
  if (params.security === "deny") {
    return { allowed: false, errorMessage: "SYSTEM_RUN_DISABLED: security=deny" };
  }

  // 2. 检查是否需要审批
  const requiresAsk = requiresExecApproval({
    ask: params.ask,
    security: params.security,
    analysisOk,
    allowlistSatisfied,
  });
  if (requiresAsk && !approvedByAsk) {
    return { allowed: false, errorMessage: "SYSTEM_RUN_DENIED: approval required" };
  }

  // 3. allowlist 模式：白名单未命中且未经审批 → 拒绝
  if (params.security === "allowlist" && !allowlistSatisfied && !approvedByAsk) {
    return { allowed: false, errorMessage: "SYSTEM_RUN_DENIED: allowlist miss" };
  }

  // 4. 通过所有检查 → 允许执行
  return { allowed: true };
}
Shell Wrapper 特殊处理

当 security=allowlist 时，shell wrapper 调用（如 bash -c "...", sh -c "..."）会被特殊拦截。因为 shell wrapper 可以执行任意命令，白名单检查在语义上无法覆盖其内部内容，因此即使外层命令匹配白名单，shell wrapper 仍会要求审批。

Tool 权限控制

除了命令执行层面的 Exec Approvals，OpenClaw 还支持在 Agent 工具层面进行细粒度的权限控制。 每个 Agent 可以配置独立的 toolPolicy，指定允许或禁止使用的工具列表。

TypeScript src/agents/sandbox-tool-policy.ts — Tool Policy 解析 
type SandboxToolPolicyConfig = {
  allow?: string[];       // 允许的工具列表（白名单）
  alsoAllow?: string[];   // 追加到白名单（不覆盖默认值）
  deny?: string[];        // 禁止的工具列表（黑名单）
};

export function pickSandboxToolPolicy(config?) {
  const allow = unionAllow(config.allow, config.alsoAllow);
  const deny = Array.isArray(config.deny) ? config.deny : undefined;
  if (!allow && !deny) return undefined;
  return { allow, deny };
}

Allow / Deny 语义

配置 效果 示例
allow: ["memory_search", "web_search"] 仅允许使用列出的工具，其他工具不可用 限制只读 Agent 只能搜索
alsoAllow: ["custom_tool"] 在默认允许的基础上追加工具 为特定 Agent 增加自定义工具
deny: ["system_run"] 禁止使用列出的工具，其他工具仍可用 禁止某个 Agent 执行系统命令
allow: ["*"] 允许所有工具（通配符） alsoAllow 无显式 allow 时的隐含行为
与 Exec Approvals 的关系

Tool Policy 和 Exec Approvals 在不同层面工作：

Tool Policy 决定 Agent 是否有权调用某个工具（在工具注入层面过滤）。

Exec Approvals 决定已经被调用的 system_run 工具的具体命令是否被允许执行（在命令执行层面审批）。

两者形成双重保护：即使 Agent 有权调用 system_run 工具，每个具体的命令仍然需要通过 Exec Approvals 的检查。

安全审计

OpenClaw 提供了一个内置的安全审计命令 openclaw security audit， 自动扫描配置文件和运行状态，检测常见的安全隐患。

Shell 安全审计命令 
openclaw security audit          // 基础审计
openclaw security audit --deep   // 包含实时 Gateway 探测
openclaw security audit --fix    // 自动修复文件权限等问题
openclaw security audit --json   // 输出机器可读的 JSON

审计发现分级

级别 含义 示例
critical 需要立即修复的高危问题 DM Policy 设为 open、群组白名单包含通配符 "*"
warn 建议关注的潜在风险 Telegram 白名单使用用户名而非 ID、多 DM 用户共享主会话
info 信息性提示 DM 已禁用（正常配置）、使用了 break-glass 兼容模式

审计检查范围

审计系统检查的范围覆盖了安全体系的各个层面：

  • 通道安全（audit-channel.ts）——每个通道的 DM Policy、Group Policy、白名单配置
  • Gateway HTTP 安全——是否启用了认证、是否存在 sessionKey 覆盖风险
  • 文件系统权限——配置文件和状态目录的 chmod 是否安全
  • Tool Policy（audit-tool-policy.ts）——per-agent 工具权限配置
  • Hooks 安全——自定义 hooks 脚本的安全性
  • 模型卫生——是否使用了不受信任的模型提供商
  • 插件安全——已安装的 Skills/Plugins 的代码安全性
  • Node 危险命令——Node host 的 allow/deny 命令模式
  • 攻击面摘要——暴露的端口和服务总览
TypeScript src/security/audit.ts — SecurityAuditFinding 类型 
export type SecurityAuditSeverity = "critical" | "warn" | "info";

export type SecurityAuditFinding = {
  checkId: string;                 // 如 "channels.telegram.dm.open"
  severity: SecurityAuditSeverity; // 严重程度
  title: string;                   // 简短描述
  detail: string;                  // 详细解释
  remediation?: string;            // 修复建议
};
审计类比

openclaw security audit 就像房屋的安全检查——检查门锁是否上好（DM Policy）、 窗户是否关严（Group Policy）、消防通道是否畅通（文件权限）、报警系统是否正常工作（Exec Approvals 配置）。 它不会替你修好所有问题，但会清楚地告诉你哪里有风险和如何修复。
