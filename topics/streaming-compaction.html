从 LLM 流式 Token 到 Channel 消息投递、从 Context Window 溢出到摘要压缩 — 两条核心数据管线的完整解析

总体架构

OpenClaw 的 Agent 运行涉及两条相互交织的数据管线：Streaming Pipeline（将 LLM 的流式响应实时投递到消息渠道）和 Compaction Pipeline（当上下文窗口接近容量时压缩对话历史）。两者都在 subscribeEmbeddedPiSession() 这一核心订阅函数中统一调度。

类比

Streaming 好比一条自来水管，LLM 的 Token 像水流一样持续流入，Block Reply 系统像一个蓄水池，攒够一定量后才放水给用户。而 Compaction 则像水管的减压阀 — 当管道压力（上下文窗口使用量）过高时，它启动压缩，把过往的长对话浓缩成一段摘要，释放管道容量。

关键设计

subscribeEmbeddedPiSession()（位于 src/agents/pi-embedded-subscribe.ts）是整个 Streaming + Compaction 管线的中枢。它订阅 Pi Agent Session 的事件流，维护一个巨大的 state 对象跟踪所有运行时状态，并通过回调函数（onBlockReply、onToolResult、onReasoningStream 等）将处理后的数据推送到渠道。

流式事件模型

Pi Agent Session 产生的事件流通过 createEmbeddedPiSessionEventHandler() 分发到不同的 handler。共有 8 种核心事件类型：

事件类型 Handler 触发时机 关键行为
message_start handleMessageStart() 新 Assistant 消息开始 重置 assistant 消息状态，触发 typing indicator
message_update handleMessageUpdate() 流式 delta/text 更新 处理 text_delta、thinking_delta、text_end；驱动 Block Reply 分块；推送 Reasoning stream
message_end handleMessageEnd() Assistant 消息结束 最终化 assistant 文本，记录 usage
tool_execution_start handleToolExecutionStart() 工具调用开始 Flush 挂起的 Block Reply，发送工具摘要
tool_execution_update handleToolExecutionUpdate() 工具执行进度 实时工具输出（verbose 模式）
tool_execution_end handleToolExecutionEnd() 工具调用结束 提交/回滚 messaging tool 文本跟踪
auto_compaction_start handleAutoCompactionStart() 自动压缩开始 设置 compactionInFlight 标志，触发 before_compaction hook
auto_compaction_end handleAutoCompactionEnd() 自动压缩结束 处理 retry 逻辑，重置 state，触发 after_compaction hook
TypeScript src/agents/pi-embedded-subscribe.handlers.ts 
export function createEmbeddedPiSessionEventHandler(ctx: EmbeddedPiSubscribeContext) {
  return (evt: EmbeddedPiSubscribeEvent) => {
    switch (evt.type) {
      case "message_start":    handleMessageStart(ctx, evt); return;
      case "message_update":   handleMessageUpdate(ctx, evt); return;
      case "message_end":      handleMessageEnd(ctx, evt); return;
      case "tool_execution_start":
        handleToolExecutionStart(ctx, evt).catch(/*...*/); return;
      case "tool_execution_update":
        handleToolExecutionUpdate(ctx, evt); return;
      case "tool_execution_end":
        handleToolExecutionEnd(ctx, evt).catch(/*...*/); return;
      case "agent_start":           handleAgentStart(ctx); return;
      case "auto_compaction_start": handleAutoCompactionStart(ctx); return;
      case "auto_compaction_end":   handleAutoCompactionEnd(ctx, evt); return;
      case "agent_end":             handleAgentEnd(ctx); return;
    }
  };
}

Thinking Tag 过滤

流式文本在投递前需要清洗 <think> / <final> 标签。stripBlockTags() 函数使用有状态的正则扫描，跨 chunk 边界追踪标签开合：

TypeScript src/agents/pi-embedded-subscribe.ts — stripBlockTags() 
const THINKING_TAG_SCAN_RE =
  /<\s*(\/?)\s*(?:think(?:ing)?|thought|antthinking)\s*>/gi;

const stripBlockTags = (text, state) => {
  // 1. 有状态地追踪 <think> 块，跳过其中的内容
  let inThinking = state.thinking;
  for (const match of text.matchAll(THINKING_TAG_SCAN_RE)) {
    // 跳过代码块内的 tag（避免误伤）
    if (codeSpans.isInside(match.index)) continue;
    // ...
    inThinking = !isClose;
  }
  state.thinking = inThinking; // 跨 chunk 保持状态

  // 2. 如果启用了 enforceFinalTag，只保留 <final> 块内的内容
  // 严格模式: 没见到 <final> 标签则返回空字符串
  if (!everInFinal) return "";
};

Block Reply 分块系统

LLM 的流式响应是逐 Token 到达的，但消息渠道（如 Telegram、Discord）不适合每个 Token 都发一条消息。Block Reply 系统将流式 Token 缓冲成合适大小的 "块"，在自然断点处发送。

EmbeddedBlockChunker

核心分块器 EmbeddedBlockChunker（位于 src/agents/pi-embedded-block-chunker.ts）使用可配置的分块策略：

参数 类型 说明
minChars number 最小缓冲字符数，低于此值不触发分块
maxChars number 最大缓冲字符数，超过时强制分块
breakPreference "paragraph" | "newline" | "sentence" 分块断点偏好
flushOnParagraph boolean 遇到 \n\n 段落边界时是否立即刷新（忽略 minChars）

export class EmbeddedBlockChunker {

Fence-safe 分块

洞察

分块器在寻找断点时会检查 Fenced Code Block 的状态。如果候选断点位于一个未闭合的 ``` 代码块内部，分块器会拒绝在此断开，以避免将不完整的代码块发送给用户。当确实需要在代码块中间断开（超过 maxChars）时，分块器会生成一对 closeFenceLine + reopenFenceLine，在断点处先关闭再重新打开代码块。

Messaging Tool 去重

当 Agent 通过 message 工具主动发送了消息，Block Reply 系统会检测并跳过重复内容，避免用户收到两条一样的消息：

TypeScript src/agents/pi-embedded-subscribe.ts — emitBlockChunk() 
const emitBlockChunk = (text: string) => {
  // 清洗 <think> 标签和降级工具文本
  const chunk = stripDowngradedToolCallText(
    stripBlockTags(text, state.blockState)
  ).trimEnd();
  if (!chunk) return;

  // 跳过与上一次发送完全相同的内容
  if (chunk === state.lastBlockReplyText) return;

  // 跳过已通过 messaging tool 发送的内容（normalized 比较）
  const normalized = normalizeTextForComparison(chunk);
  if (isMessagingToolDuplicateNormalized(
    normalized, messagingToolSentTextsNormalized
  )) {
    log.debug(`Skipping block reply - already sent via messaging tool`);
    return;
  }

  state.lastBlockReplyText = chunk;
  assistantTexts.push(chunk);
  // 解析 reply directives 后投递
  emitBlockReplySafely({ text: cleanedText, mediaUrls, ... });
};

Compaction 触发机制

当对话越来越长，上下文窗口（Context Window）逐渐被填满。Compaction 是 OpenClaw 自动压缩对话历史的机制，防止超出模型的 Token 上限。

Compaction 触发流程
Context Window 使用量监控
超过阈值
auto_compaction_start 事件
summarize
旧消息替换为摘要

触发方式

触发方式 入口函数 说明
Overflow 自动触发 Pi Agent 内核的 auto_compaction_start 事件 当 Token 使用量接近 Context Window 上限时，Pi Agent 自动发起 Compaction，通过事件通知 OpenClaw
手动触发 compactEmbeddedPiSession() 用户通过 /compact 命令手动触发，走 session lane + global lane 队列
Direct 模式 compactEmbeddedPiSessionDirect() 已在 lane 内部时使用，避免死锁

分阶段摘要算法

Compaction 的核心是将旧对话消息压缩成一段摘要。这由 src/agents/compaction.ts 中的 summarizeInStages() 函数实现，采用分段-合并策略处理大量消息。

分阶段摘要流程
消息列表
messages[]
splitMessagesByTokenShare
分段摘要
chunk1 -> summary1
chunk2 -> summary2
merge summaries
最终合并摘要

核心算法参数

常量 值 说明
BASE_CHUNK_RATIO 0.4 基础分块比例，chunk 大小 = contextWindow * 0.4
MIN_CHUNK_RATIO 0.15 最小分块比例（当消息平均很大时降低）
SAFETY_MARGIN 1.2 20% 安全缓冲区，补偿 estimateTokens() 的低估
SUMMARIZATION_OVERHEAD_TOKENS 4,096 摘要 prompt 本身的 Token 开销预留
DEFAULT_PARTS 2 默认将消息分成 2 段

自适应分块比例

TypeScript src/agents/compaction.ts — computeAdaptiveChunkRatio() 
// 当消息平均大小 > 上下文窗口的 10% 时，动态缩小分块比例
export function computeAdaptiveChunkRatio(
  messages: AgentMessage[],
  contextWindow: number,
): number {
  const totalTokens = estimateMessagesTokens(messages);
  const avgTokens = totalTokens / messages.length;
  const safeAvgTokens = avgTokens * SAFETY_MARGIN;
  const avgRatio = safeAvgTokens / contextWindow;

  if (avgRatio > 0.1) {
    // 消息很大，缩小 chunk ratio 以避免超限
    const reduction = Math.min(
      avgRatio * 2,
      BASE_CHUNK_RATIO - MIN_CHUNK_RATIO
    );
    return Math.max(MIN_CHUNK_RATIO, BASE_CHUNK_RATIO - reduction);
  }
  return BASE_CHUNK_RATIO; // 0.4
}

渐进式回退

summarizeWithFallback() 实现了三级回退策略：

  1. 完整摘要：尝试对所有消息进行分块摘要
  2. 部分摘要：如果失败，排除超大消息（单条 > 50% contextWindow），只摘要小消息
  3. 元数据回退：如果连部分摘要也失败，返回 "Context contained N messages (M oversized). Summary unavailable."
TypeScript src/agents/compaction.ts — isOversizedForSummary() 
// 单条消息 > 50% 上下文窗口就判定为"过大"
export function isOversizedForSummary(
  msg: AgentMessage,
  contextWindow: number,
): boolean {
  const tokens = estimateCompactionMessageTokens(msg) * SAFETY_MARGIN;
  return tokens > contextWindow * 0.5;
}
安全设计

toolResult.details 字段可能包含不受信任的大量数据。摘要函数在处理前会通过 stripToolResultDetails() 移除这些字段，确保：(1) 不会有不可信内容注入到 LLM 摘要 prompt 中，(2) Token 估算更准确。

Compaction Safeguard 扩展

默认的 Pi Agent 摘要算法过于简单，可能丢失关键信息。OpenClaw 通过 compaction-safeguard 扩展（位于 src/agents/pi-extensions/compaction-safeguard.ts）覆写了整个压缩流程，提供结构化摘要和质量保障。

结构化摘要格式

Safeguard 强制生成包含以下 5 个必需段落的摘要：

段落标题 说明
## Decisions 已做出的决策及其理由
## Open TODOs 尚未完成的任务
## Constraints/Rules 当前约束和规则
## Pending user asks 用户尚未得到回答的请求
## Exact identifiers 需要精确保留的标识符（UUID, URL, 路径等）

Identifier Preservation 策略

标识符保留支持三种策略（AgentCompactionIdentifierPolicy）：

策略 行为
"strict"（默认） 强制保留所有 opaque identifiers（UUID, hash, URL, 路径, IP:port 等）。Quality Guard 会检查缺失的标识符
"custom" 使用运营者自定义的保留指令
"off" 不强制保留标识符

Quality Guard（质量审计）

Safeguard 可选地启用质量审计，在生成摘要后检查：

TypeScript src/agents/pi-extensions/compaction-safeguard.ts — auditSummaryQuality() 
function auditSummaryQuality(params: {
  summary: string;
  identifiers: string[];
  latestAsk: string | null;
  identifierPolicy?: "strict" | "off" | "custom";
}): { ok: boolean; reasons: string[] } {
  const reasons: string[] = [];

  // 1. 检查 5 个必需段落是否都存在
  for (const section of REQUIRED_SUMMARY_SECTIONS) {
    if (!lines.has(section)) reasons.push(`missing_section:${section}`);
  }

  // 2. 检查关键标识符是否保留（strict 模式）
  if (enforceIdentifiers) {
    const missing = identifiers.filter(
      id => !summaryIncludesIdentifier(summary, id)
    );
    if (missing.length > 0) reasons.push(`missing_identifiers:...`);
  }

  // 3. 检查最近用户请求是否被反映（token overlap 检测）
  if (!hasAskOverlap(summary, latestAsk)) {
    reasons.push("latest_user_ask_not_reflected");
  }

  return { ok: reasons.length === 0, reasons };
}

如果审计失败，Safeguard 会重试（最多 qualityGuardMaxRetries 次，默认 1 次），在重试 prompt 中附带失败原因反馈。

Recent Turns 保留

Safeguard 支持保留最近 N 轮对话原文（默认 3 轮，最大 12 轮），不参与摘要，直接附加到摘要尾部的 ## Recent turns preserved verbatim 段落中。这确保 Agent 对"刚才在做什么"有精确记忆。

附加上下文

摘要还会自动附加以下信息：

  • Tool Failures：最近的工具失败记录（最多 8 条），包括工具名、退出码、错误摘要
  • File Operations：读取和修改的文件列表（<read-files> / <modified-files>）
  • Workspace Critical Rules：从 AGENTS.md 中提取 "Session Startup" 和 "Red Lines" 段落（最多 2000 字符），确保关键规则在 compaction 后不丢失

Memory Flush 与超时保护

Compaction 过程中存在多个保护机制，防止数据丢失和资源泄漏。

安全超时

TypeScript src/agents/pi-embedded-runner/compaction-safety-timeout.ts 
// Compaction 有 5 分钟的硬超时
export const EMBEDDED_COMPACTION_TIMEOUT_MS = 300_000; // 5 min

export async function compactWithSafetyTimeout<T>(
  compact: () => Promise<T>,
  timeoutMs = EMBEDDED_COMPACTION_TIMEOUT_MS,
): Promise<T> {
  return await withTimeout(() => compact(), timeoutMs, "Compaction");
}

Pre-Compaction Snapshot

当 Compaction 超时时，系统需要决定使用哪个消息快照来构建最终响应：

TypeScript src/agents/pi-embedded-runner/run/compaction-timeout.ts 
export function selectCompactionTimeoutSnapshot(
  params: SnapshotSelectionParams,
): SnapshotSelection {
  // 如果 Compaction 超时了，优先使用压缩前的快照
  if (params.timedOutDuringCompaction && params.preCompactionSnapshot) {
    return {
      messagesSnapshot: params.preCompactionSnapshot,
      sessionIdUsed: params.preCompactionSessionId,
      source: "pre-compaction",  // 安全回退
    };
  }
  // 否则使用当前（可能已压缩的）快照
  return {
    messagesSnapshot: params.currentSnapshot,
    sessionIdUsed: params.currentSessionId,
    source: "current",
  };
}

Compaction Retry 与 Promise 协调

Overflow 触发的 Compaction 可能需要重试（willRetry=true）。subscribe 层通过一组 Promise 协调等待：

TypeScript src/agents/pi-embedded-subscribe.ts — Compaction 协调 
// State 中的 compaction 追踪字段
state = {
  compactionInFlight: false,    // 是否有 compaction 正在进行
  pendingCompactionRetry: 0,    // 待完成的 retry 计数
  compactionRetryPromise: null, // 等待 retry 完成的 Promise
};

// auto_compaction_end handler 中：
if (willRetry) {
  ctx.noteCompactionRetry();      // pendingCompactionRetry++
  ctx.resetForCompactionRetry();  // 重置 assistantTexts, toolMetas 等
} else {
  ctx.maybeResolveCompactionWait(); // resolve pending promise
}

// 外层 run 逻辑等待 compaction 完成
await subscription.waitForCompactionRetry();
注意: Unsubscribe 安全

当 unsubscribe() 被调用时，如果 Compaction 仍在运行：(1) pending promise 会被 reject（使用 AbortError），避免调用者永远挂起；(2) session.abortCompaction() 被调用以取消进行中的 LLM 请求。这防止了资源泄漏和悬挂的 Promise。

Block Reply Flush 保护

在 agent_end 事件中，系统会先 flush 所有挂起的 Block Reply，再等待 Compaction 完成。这确保用户的回复不会被 Compaction 的长时间等待阻塞：

TypeScript src/agents/pi-embedded-subscribe.handlers.lifecycle.ts 
export function handleAgentEnd(ctx: EmbeddedPiSubscribeContext) {
  // 1. 先 flush 所有缓冲的回复文本
  ctx.flushBlockReplyBuffer();

  // 2. 通知渠道层立即投递（不等 compaction）
  void ctx.params.onBlockReplyFlush?.();

  // 3. 最后处理 compaction wait
  if (ctx.state.pendingCompactionRetry > 0) {
    ctx.resolveCompactionRetry();
  } else {
    ctx.maybeResolveCompactionWait();
  }
}

完整生命周期

将 Streaming 和 Compaction 合并，一次 Agent Run 的完整生命周期如下：

阶段 事件 / 动作 Streaming 行为 Compaction 行为
1. 初始化 agent_start 创建订阅，初始化 state -
2. 首轮回复 message_start -> message_update(n) -> message_end 流式 Token -> Block Chunker -> Channel -
3. 工具调用 tool_execution_start -> tool_execution_end Flush Block Reply, 发送工具摘要 -
4. 后续回复 message_start -> ... -> message_end 继续流式投递 -
5. Context 溢出 auto_compaction_start compactionInFlight = true 开始结构化摘要生成
6. 摘要完成 auto_compaction_end 如 willRetry: 重置所有 streaming state 旧消息替换为摘要，可能 retry LLM 请求
7. 重试回复 message_start -> ... (使用压缩后上下文) 全新一轮流式投递 -
8. 结束 agent_end Flush 剩余 buffer，解析 usage Resolve compaction wait promise
关键点: Compaction 时的 State 重置

当 auto_compaction_end 带有 willRetry=true 时，resetForCompactionRetry() 会清空所有已收集的 assistant 文本、工具元数据、messaging tool 追踪等。这确保 Compaction 后 Agent 的重试回复以干净状态开始，不会与压缩前的残留数据混合。

Hook 生命周期

Compaction 的前后各触发两层 Hook：

时机 Internal Hook Plugin Hook 传递的元数据
压缩前 session:compact:before before_compaction messageCount, tokenCount, sessionId
压缩后 session:compact:after after_compaction messageCount, tokenCount, compactedCount, summaryLength, tokensBefore, tokensAfter
