为什么需要并发控制

OpenClaw 是一个多通道 AI 网关，同时连接 Telegram、Discord、Slack、Signal 等多个消息平台。 在生产环境中，Gateway 进程随时可能面临这样的场景：

  • 用户 Alice 在 Telegram 发了一条消息，Agent 正在生成回复
  • 用户 Bob 在 Discord 同时发了一条消息
  • 一个定时任务（cron）触发了每日摘要
  • Alice 等不及，又追加发了第二条消息

如果这些任务不加控制地并发执行，就会出现严重问题——尤其是 Alice 的两条消息被两个 Agent 同时处理， 两个 Agent 会同时读写 Alice 的对话历史，导致上下文冲突、回复错乱。

核心问题

并发冲突：同一会话的多条消息如果被并行处理，Agent 会同时读写对话上下文，导致数据不一致和回复错乱。

Lane Queue 的设计目标就是："Only one agent run touches a given session at a time"（同一时间只有一个 Agent 能操作某个会话）。

车道类型一览

Lane Queue 采用高速公路收费站的设计思路：多条车道并行，每条车道有独立的通行规则和限速。 任务按类型被分配到不同车道，车道之间互不干扰。

双层排队机制

核心洞察

session:<key> 和 main 看起来都在处理聊天任务，但它们并不重复——而是分别解决不同层面的问题，形成双层排队。

一个 Agent 任务执行前，会经过两层队列的筛选。我们来看源码中的实际实现：

TypeScript src/agents/pi-embedded-runner/run.ts:274-275 
return enqueueSession(() =>        // 第 1 层：进入 session:alice 排队
    enqueueGlobal(async () => {    // 第 2 层：进入 main 排队
      // ... 真正执行 Agent 任务
    })
);

双层排队的执行流程

任务如何穿越两层队列
第 1 层：session:alice（并发 1）
保证 Alice 的消息严格按顺序，一条处理完再处理下一条
获得 session 许可后
第 2 层：main（并发 4）
控制全系统同时运行的 Agent 总数，防止过载
获得全局许可后
执行 Agent 任务
调用 AI 模型、生成回复、写入对话历史

为什么两层都不可缺少？

如果只有 session，没有 main

100 个用户同时发消息 → 100 个 session 车道各放行 1 个任务 → 100 个 Agent 同时运行 → CPU、内存、API 调用配额全部过载，系统崩溃。

如果只有 main，没有 session

Alice 连发 3 条消息 → 3 条可能同时占据 main 的 3 个槽位 → 3 个 Agent 同时读写 Alice 的对话历史 → 上下文冲突，回复混乱。

两层配合：session 管顺序，main 管总量

session:alice 保证 Alice 的 3 条消息排队串行 → 每次只有 1 条进入 main → main 保证全系统最多 4 个 Agent 同时运行。既安全，又高效。

时间线示例
事件 session 车道 main 车道 结果

Pump 自驱动引擎

队列的核心调度逻辑是一个自驱动的泵（pump）——不需要外部定时器或轮询线程， 每个任务完成后会自动检查并启动下一个任务。

TypeScript src/process/command-queue.ts — drainLane 核心逻辑 
const pump = () => {
  try {
    // 只要：正在执行的任务数 < 最大并发数 且 队列中还有等待的任务
    while (state.activeTaskIds.size < state.maxConcurrent && state.queue.length > 0) {
      const entry = state.queue.shift();  // 取出队头任务
      const taskId = nextTaskId++;
      state.activeTaskIds.add(taskId);

      void (async () => {
        try {
          const result = await entry.task();  // 执行任务
          completeTask(state, taskId, taskGeneration);
          pump();                              // 完成后，再次泵送下一个！
          entry.resolve(result);               // 通知调用方
        } catch (err) {
          completeTask(state, taskId, taskGeneration);
          pump();                              // 即使失败，也继续泵送
          entry.reject(err);
        }
      })();
    }
  } finally {
    state.draining = false;
  }
};

流程可以简化为三步循环：

  1. 任务入队 → 调用 enqueueCommandInLane()，任务被放入对应车道的队列尾部
  2. 触发 drain → 调用 drainLane()，启动 pump
  3. pump 循环 → 取出队头、执行、完成后再次 pump → 自动驱动下一个任务
生活类比

想象一条传送带：工人取走一个包裹、处理完毕后，传送带自动向前滚动，下一个包裹自动到位。 不需要有人站在旁边喊"下一个"——完成本身就是启动下一个的信号。

Promise 机制解析

整个队列系统是用 JavaScript 的 Promise 构建的。如果你不熟悉 Promise， 可以把它理解为——餐厅的叫号器。

叫号器类比

你去餐厅点餐：

1. 你点了一份牛排 → 发起异步操作

2. 服务员给你一个叫号器 → 你拿到一个 Promise

3. 你可以去做别的事（看手机、聊天） → 程序继续执行其他代码，不用干等

4. 叫号器响了 → Promise 变为 Fulfilled（完成）

5. 你去取餐 → 获得结果

Promise 的三种状态

Pending
等待中
→
Fulfilled
成功，拿到结果
Rejected
失败，拿到原因

Promise 在队列中的角色

看 enqueueCommandInLane 的核心代码：

TypeScript src/process/command-queue.ts:175-186 
return new Promise<T>((resolve, reject) => {
  // 把任务放进队列，同时把 resolve/reject 也存起来
  state.queue.push({
    task: () => task(),
    resolve,      // ← "叫号器的按钮"——任务完成时按这个通知调用方
    reject,       // ← 任务失败时按这个
    enqueuedAt: Date.now(),
    warnAfterMs,
  });
  drainLane(cleaned);   // 尝试启动队列
});

整个流程是：

  1. 调用方调用 enqueueCommandInLane() → 拿到一个 Promise（叫号器）
  2. 任务被放进队列等待，调用方可以 await 这个 Promise
  3. 轮到它执行时，pump() 取出任务并运行
  4. 任务跑完 → 调用 resolve(result) → 调用方的 Promise 收到结果，被唤醒
关键优势

Promise 充当通知机制——调用方不用轮询"我的任务完了没？"，只需要 await，任务完成时会自动被通知。

这是一种推送模型（push）而非拉取模型（poll），零 CPU 消耗等待。

为什么不需要 Redis

传统的消息队列系统通常依赖 Redis、RabbitMQ 等外部中间件。 OpenClaw 选择了纯进程内实现，这不是偷懒——而是架构决策的精确匹配。

能力 Redis 方案 Promise 队列方案
任务排队 List（LPUSH / RPOP） Array（push / shift）
完成通知 Pub/Sub 或轮询 Promise resolve（零延迟）
并发控制 分布式锁 / Lua 脚本 activeTaskIds.size < maxConcurrent
跨进程共享 支持 不支持
跨机器共享 支持 不支持
运维成本 需要部署、监控、维护 Redis 实例 零——代码即基础设施
延迟 网络往返（~1ms） 微秒级（进程内调用）
架构决策

OpenClaw Gateway 是单进程架构——所有消息通道的请求都在同一个 Node.js 进程中处理。 进程内的 Map + Array + Promise 已经完全满足需求。

引入 Redis 不会带来任何好处，反而增加部署复杂度、网络延迟和运维负担。 不是 Promise 比 Redis 更强，而是在单进程场景下，简单方案就是最优方案。

类比

如果你是连锁餐厅（多进程、多机器），叫号系统确实需要一个中央服务器（Redis）来跨门店协调。 但如果你是单体小餐厅（单进程），一个本地叫号器就完全够用——花钱装中央系统反而是浪费。
