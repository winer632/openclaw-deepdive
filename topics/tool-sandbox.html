Tool 系统与 Sandbox 沙箱

从 25 个核心工具到无限 Plugin 扩展，经过 7 层 Policy 过滤管线， 在 Docker 容器中安全执行。理解 OpenClaw 如何在 Agent 的开放性与操作系统级安全隔离之间取得精确平衡。

Tool 注册与 Catalog

OpenClaw 的工具系统是 Agent 与外部世界交互的唯一通道。每个工具都在 tool-catalog.ts 中进行声明式注册，通过 CoreToolDefinition 定义唯一 ID、所属分区（section） 和所属 Profile。系统启动时动态组装工具列表，而非静态配置。

11 个工具分区

分区 (Section) 包含的工具 Group 引用
Files read, write, edit, apply_patch group:fs
Runtime exec, process group:runtime
Web web_search, web_fetch group:web
Memory memory_search, memory_get group:memory
Sessions sessions_list, sessions_history, sessions_send, sessions_spawn, subagents, session_status group:sessions
UI browser, canvas group:ui
Messaging message group:messaging
Automation cron, gateway group:automation
Nodes nodes group:nodes
Agents agents_list group:agents
Media image, tts group:media

4 种 Tool Profile

Profile 是工具组合的预设方案，通过 tools.profile 配置项选择：

minimal

仅包含 session_status。纯对话场景，Agent 无编码/执行能力。

coding

文件 + 运行时 + Web + Memory + Sessions。编码助手的标准配置。

messaging

message + Sessions 子集。多通道消息路由场景。

full

不设 allow/deny 限制——所有工具（含 Plugin）全部可用。

TypeScript src/agents/tool-catalog.ts — CoreToolDefinition 
type CoreToolDefinition = {
  id: string;                      // 工具唯一标识 (如 "exec")
  label: string;                   // 显示名称
  description: string;             // 工具描述
  sectionId: string;               // 所属分区 (如 "runtime")
  profiles: ToolProfileId[];       // 属于哪些 Profile
  includeInOpenClawGroup?: boolean; // 是否纳入 group:openclaw
};
核心洞察

group:openclaw 是一个特殊的工具组，包含所有标记了 includeInOpenClawGroup: true 的工具（25 个核心工具中的绝大多数）。配置 tools.allow: ["group:openclaw"] 即可启用全部核心工具，而不受 Plugin 工具干扰。

7 层 Policy 过滤管线

工具组装完毕后，需要经过 applyToolPolicyPipeline() 的7 层过滤。 每一层都可以通过 allow（白名单）和 deny（黑名单）控制工具可见性。 当某一层配置了 allow 列表时，只有被列入的工具才能通过；所有层的 deny 都会立即排除匹配的工具。

buildDefaultToolPolicyPipelineSteps() 定义的 7 层管线
Layer 1: tools.profile
全局 Profile 策略（minimal / coding / messaging / full）
Layer 2: tools.byProvider.profile
按 AI 提供商（Anthropic / OpenAI / Google）覆盖 Profile
Layer 3: tools.allow / tools.deny
全局工具白/黑名单
Layer 4: tools.byProvider.allow
按 AI 提供商的工具白/黑名单
Layer 5: agents.<id>.tools.allow
特定 Agent 的工具策略
Layer 6: agents.<id>.tools.byProvider.allow
特定 Agent 按提供商的工具策略
Layer 7: group tools.allow
群组/频道级别的工具策略

Plugin-Only Allowlist 保护

每一层在执行前都会调用 stripPluginOnlyAllowlist()，检测 allowlist 中是否仅包含 Plugin 工具名。 如果是，则自动剥离该 allowlist，防止管理员误配导致所有核心工具被意外禁用。 用户应使用 tools.alsoAllow 来追加Plugin 工具，而非替换核心工具。

TypeScript src/agents/tool-policy-pipeline.ts — applyToolPolicyPipeline 
export function applyToolPolicyPipeline(params: {
  tools: AnyAgentTool[];
  toolMeta: (tool: AnyAgentTool) => { pluginId: string } | undefined;
  warn: (message: string) => void;
  steps: ToolPolicyPipelineStep[];
}): AnyAgentTool[] {
  let filtered = params.tools;
  for (const step of params.steps) {
    if (!step.policy) continue;
    // 检测并剥离仅含 Plugin 工具的 allowlist
    const resolved = stripPluginOnlyAllowlist(policy, pluginGroups, coreToolNames);
    if (resolved.unknownAllowlist.length > 0) {
      params.warn(`${step.label} contains unknown entries...`);
    }
    const expanded = expandPolicyWithPluginGroups(resolved.policy, pluginGroups);
    filtered = expanded ? filterToolsByPolicy(filtered, expanded) : filtered;
  }
  return filtered;
}

生活类比

想象一个机场安检流程：旅客先过护照检查（Profile），再过行李 X 光机（全局策略）， 然后过登机口核验（Agent 级策略），最后过机上安检（群组策略）。 每一关都可以拦截可疑物品（deny）或只放行已申报物品（allow）。 最终登机的只有所有关卡都通过的工具。

Plugin 工具扩展

除了 25 个核心工具，OpenClaw 支持通过 extensions/* 目录下的 Plugin 注册自定义工具。 Plugin 工具与核心工具共享相同的 Policy 管线，但有额外的安全机制。

Plugin 工具加载流程

resolvePluginTools() 加载管线
1. 发现 Plugins
loadOpenClawPlugins() 扫描 extensions/* 和 config 中声明的插件
registry.tools
2. 名称冲突检测
Plugin ID 和工具名不能与核心工具重名，否则被 block
factory(context)
3. 实例化 & 元数据标记
WeakMap 标记 pluginId + optional 属性
TypeScript src/plugins/tools.ts — Plugin 工具元数据追踪 
const pluginToolMeta = new WeakMap<AnyAgentTool, PluginToolMeta>();

type PluginToolMeta = {
  pluginId: string;    // 来源插件标识
  optional: boolean;   // 是否为可选工具（需要 allowlist 显式启用）
};

// 每个 Plugin 工具都通过 WeakMap 标记来源
// 用于后续 Policy 管线中的 group:plugins 展开
pluginToolMeta.set(tool, { pluginId: entry.pluginId, optional: entry.optional });

Plugin Group 展开机制

Policy 中可以使用 group:plugins 引用所有 Plugin 工具， 或直接使用 Plugin ID（如 feishu）引用该插件注册的所有工具。 expandPluginGroups() 在 Policy 匹配时将这些逻辑组展开为具体工具名列表。

设计亮点

Optional Tools 的 Opt-in 设计：标记为 optional: true 的 Plugin 工具默认不加载。只有在 tools.alsoAllow 中显式列出工具名、Plugin ID、或 group:plugins 时才会启用。这避免了安装 Plugin 后工具自动暴露给所有 Agent 的风险。

Hook 执行生命周期

即使工具通过了 Policy 过滤，在实际执行时还有一道防线——Plugin Hooks。 Hooks 是 OpenClaw 的事件系统，Plugin 可以监听 before_tool_call、after_tool_call 等事件，在工具执行前后介入。

Tool 执行完整生命周期
1. Tool Loop Detection
检测重复调用模式（同一工具 + 同参数），critical 级别直接阻断
通过检测
2. before_tool_call Hook
按 priority 顺序执行，可修改参数或返回 block: true 阻断
未被阻断
3. tool.execute()
实际执行工具逻辑（宿主机或 Docker 容器内）
执行完毕
4. after_tool_call Hook
并行执行（fire-and-forget），不影响工具结果
结果持久化
5. tool_result_persist Hook
同步钩子，可修改写入会话日志的结果
Hook 执行模式 返回值影响 典型用途
before_tool_call 顺序（按 priority） 可修改 params / 返回 block 参数校验、审计、阻断危险操作
after_tool_call 并行（fire-and-forget） void 日志记录、指标收集
tool_result_persist 顺序（同步） 可替换 message 脱敏、压缩写入会话的结果

Hook 来源与发现

Hook 可以来自四种来源，按优先级加载：

来源 路径 说明
openclaw-bundled src/hooks/bundled/ 内置 Hook：boot-md、session-memory、command-logger 等
openclaw-managed ~/.openclaw/hooks/ 用户安装的 Hook（npm / git）
openclaw-workspace {workspace}/.openclaw/hooks/ 项目级 Hook
openclaw-plugin extensions/*/ Plugin 提供的 Hook
安全设计

before_tool_call 的修改型设计允许多个 Plugin 链式协作：一个负责审计日志，另一个负责参数脱敏，第三个负责访问控制。而 after_tool_call 的观察型设计保证即使某个 Plugin 出错，也不会阻塞工具链返回结果。

Docker 沙箱架构

当 agents.defaults.sandbox.mode 设为 "non-main" 或 "all" 时， OpenClaw 会为 Agent 会话创建独立的 Docker 容器，将 exec、read、write 等工具的执行隔离在容器中。

为什么需要沙箱

AI Agent 的 exec 工具可以执行任意 Shell 命令。在没有沙箱的情况下，一个被误导的 Agent 可能删除系统文件、泄露敏感数据、或攻击内网服务。Docker 沙箱将"爆炸半径"限制在容器内部，提供操作系统级隔离。

默认容器安全参数

Docker 参数 默认值 安全作用
--read-only true 只读根文件系统，防止写入系统目录
--network none 完全隔离网络，禁止外部访问
--cap-drop ALL 丢弃所有 Linux capabilities
--security-opt no-new-privileges 禁止进程获取新权限（防 suid 提权）
--tmpfs /tmp, /var/tmp, /run 临时文件系统，重启后清空
--pids-limit 可配置 限制容器进程数，防止 fork bomb
--memory 可配置 内存上限，防止 OOM 宿主机
--cpus 可配置 CPU 配额限制
TypeScript src/agents/sandbox/docker.ts — buildSandboxCreateArgs (核心) 
// 1. 运行时安全验证
validateSandboxSecurity({ ...params.cfg, allowedSourceRoots, ... });

// 2. 构建 docker create 参数
const args = ["create", "--name", params.name];
args.push("--label", "openclaw.sandbox=1");
args.push("--label", `openclaw.sessionKey=${params.scopeKey}`);
args.push("--label", `openclaw.configHash=${params.configHash}`);
if (params.cfg.readOnlyRoot) args.push("--read-only");
for (const entry of params.cfg.tmpfs) args.push("--tmpfs", entry);
args.push("--network", params.cfg.network);        // 默认 "none"
for (const cap of params.cfg.capDrop) args.push("--cap-drop", cap);  // 默认 ["ALL"]
args.push("--security-opt", "no-new-privileges");

// 3. 环境变量消毒
const envSanitization = sanitizeEnvVars(params.cfg.env ?? {});
// 自动屏蔽 API key、token 等敏感环境变量
生活类比

Docker 沙箱就像一间安全实验室：Agent 在密封房间里工作， 有白板（workspace 挂载）和临时桌子（tmpfs），但没有网络（network=none）、 没有电话、门锁从外面控制（no-new-privileges），且墙壁是防弹玻璃（read-only root）。 Agent 可以在白板上自由操作，但无法影响实验室外的世界。

3 级 Sandbox Scope

并非每次 Agent 调用都创建新容器。SandboxScope 控制容器的共享粒度， 在隔离性和资源效率之间取得平衡。

Scope 容器共享范围 容器命名 适用场景
session 每个会话独享容器 openclaw-sbx-{sessionKey} 最高隔离：不同用户的容器完全独立
agent 同一 Agent 的所有会话共享 openclaw-sbx-{agentId} 平衡模式（默认）
shared 所有 Agent 共享一个容器 openclaw-sbx-shared 最低资源消耗

Sandbox Tool Policy

Sandbox 有独立的工具策略层 resolveSandboxToolPolicyForAgent()，控制容器内可以使用哪些工具。 默认配置中，允许文件/运行时/会话工具，拒绝浏览器/通道/自动化工具：

TypeScript src/agents/sandbox/constants.ts — 默认 Sandbox 工具策略 
export const DEFAULT_TOOL_ALLOW = [
  "exec", "process", "read", "write", "edit", "apply_patch",

  "sessions_spawn", "subagents", "session_status",
] as const;

export const DEFAULT_TOOL_DENY = [
  "browser", "canvas", "nodes", "cron", "gateway",
  ...CHANNEL_IDS,  // telegram, discord, slack, signal, imessage, web ...

容器生命周期：Config Hash 与热窗口

容器不是用完即弃的。ensureSandboxContainer() 通过 computeSandboxConfigHash() 比对当前配置与容器标签中的哈希值，决定复用还是重建。 如果容器在最近 5 分钟内被使用（HOT_CONTAINER_WINDOW_MS）， 即使配置变更也不会自动销毁，而是提示用户手动 openclaw sandbox recreate。

清理策略 默认值 说明
idleHours 24 小时 未使用超过此时间自动清理
maxAgeDays 7 天 超过此年龄一律清理

容器安全与 Bind Mount 验证

validateSandboxSecurity() 在每次创建容器时执行运行时安全检查， 即使配置来自受信任的本地文件，也要防止足枪（foot-gun）和配置注入。

Bind Mount 黑名单

以下宿主机路径永远不允许挂载到容器中：

TypeScript src/agents/sandbox/validate-sandbox-security.ts — BLOCKED_HOST_PATHS 
export const BLOCKED_HOST_PATHS = [
  "/etc", "/private/etc",      // 系统配置
  "/proc", "/sys", "/dev",     // 内核接口
  "/root", "/boot",            // 特权目录
  "/run", "/var/run",          // Docker socket 所在目录
  "/private/var/run",
  "/var/run/docker.sock",      // Docker socket 本身
  "/private/var/run/docker.sock",
  "/run/docker.sock",
];

Seccomp / AppArmor 限制

unconfined 的 seccomp 或 AppArmor profile 被明确禁止。 此外，预留的容器内路径 /workspace 和 /agent 不允许被自定义 bind mount 覆盖。

3 个 Dangerous 旗标

配置项 效果 风险
dangerouslyAllowReservedContainerTargets 允许 bind mount 到 /workspace 和 /agent 可能覆盖 Agent 的工作目录
dangerouslyAllowExternalBindSources 允许挂载 allowedSourceRoots 之外的路径 扩大宿主机暴露面
dangerouslyAllowContainerNamespaceJoin 允许 container:xxx 网络模式 容器间网络隔离失效
环境变量消毒

sanitizeEnvVars() 会自动屏蔽名称中包含 KEY、TOKEN、SECRET、PASSWORD 等模式的环境变量，防止 API 密钥泄露到容器内。被屏蔽的变量会记录在 envSanitization.blocked 中用于审计。
