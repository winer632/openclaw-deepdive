双层架构（CDP + Playwright）

OpenClaw 的浏览器自动化不是简单地调用 Playwright API，而是构建了一个双层架构： 底层直接使用 Chrome DevTools Protocol（CDP） 进行底层通信， 上层通过 Playwright 提供高级页面操作抽象。

底层：CDP 直连

通过 WebSocket 直接与 Chrome/Chromium 的 DevTools Protocol 通信。 用于底层操作：截图（Page.captureScreenshot）、 Accessibility Tree 获取（Accessibility.getFullAXTree）、 网络拦截等。

上层：Playwright

通过 chromium.connectOverCDP() 连接已有浏览器实例。 提供高级 API：点击、填表、导航、等待、Snapshot、 Cookie/Storage 管理等。

为什么需要双层

CDP 层提供了 Playwright 不暴露的底层能力（如 Accessibility Tree 原始数据、精细的协议级控制），并支持 WebSocket URL 重写（containerized browser 场景）。

Playwright 层提供了可靠的高级自动化 API（自动等待、智能定位、事件监听），并且通过 _snapshotForAI 接口提供 AI 友好的页面快照。

CDP URL 规范化

容器化浏览器（如 Docker sandbox 或 Browserless）报告的 WebSocket URL 可能是内部地址（如 ws://0.0.0.0:9222）。 normalizeCdpWsUrl() 负责将这些地址重写为外部可达的地址：

TypeScript src/browser/cdp.ts — normalizeCdpWsUrl 
export function normalizeCdpWsUrl(wsUrl: string, cdpUrl: string): string {
  const ws = new URL(wsUrl);
  const cdp = new URL(cdpUrl);
  // 0.0.0.0 和 [::] 是通配绑定地址，需要重写为外部 host:port
  const isWildcardBind = ws.hostname === "0.0.0.0" || ws.hostname === "[::]";
  if ((isLoopbackHost(ws.hostname) || isWildcardBind) && !isLoopbackHost(cdp.hostname)) {
    ws.hostname = cdp.hostname;
    ws.port = cdp.port || (cdp.protocol === "https:" ? "443" : "80");
    ws.protocol = cdp.protocol === "https:" ? "wss:" : "ws:";
  }
  // 继承 cdp URL 的认证信息和查询参数
  if (!ws.username && (cdp.username || cdp.password)) {
    ws.username = cdp.username;
    ws.password = cdp.password;
  }
  return ws.toString();
}

Browser Profiles

OpenClaw 支持多个浏览器 Profile 并行运行，每个 Profile 对应一个独立的 CDP 端点。 Profile 不是 Chrome User Profile——它是 OpenClaw 的路由配置，决定浏览器命令发往哪个 CDP 端点。

Profile 模式 Driver 说明 典型场景
openclaw openclaw OpenClaw 管理的独立 Chromium 实例（自动启停） 自动化测试、数据采集、隔离浏览
chrome extension 通过 Chrome Extension Relay 接管用户现有 Chrome 标签页 操作已登录的网站、实时协作
remote / custom openclaw 连接远程 CDP 端点（如 Browserless、Docker 沙箱浏览器） 无头浏览器服务、Sandbox 模式

Profile 配置解析

TypeScript src/browser/config.ts — resolveProfile 
export type ResolvedBrowserProfile = {
  name: string;
  cdpPort: number;          // CDP 端口
  cdpUrl: string;           // 完整 CDP URL
  cdpHost: string;          // CDP 主机名
  cdpIsLoopback: boolean;   // 是否本地回环
  color: string;            // UI 标识颜色（如工具栏徽章颜色）
  driver: "openclaw" | "extension";  // 驱动模式
  attachOnly: boolean;      // 仅连接（不自动启动浏览器）
};

Snapshot 系统

浏览器自动化的核心挑战是：Agent 如何"看到"网页？ 截图是一种方式，但截图占用大量 token 且难以精确定位元素。 OpenClaw 提供了两种文本化的页面快照机制，让 Agent 以极低的 token 成本"理解"页面结构。

AI Snapshot

基于 Playwright 的 _snapshotForAI() 接口。返回 AI 友好的页面结构文本， 包含可交互元素的 aria-ref ID。Agent 可直接使用这些 ref 进行操作。

Role Snapshot

基于 Playwright 的 ariaSnapshot() 或 CDP 的 Accessibility.getFullAXTree。 解析 ARIA 角色树，为每个可交互元素生成 e1/e2/e3... 引用 ID。

AI Snapshot 工作流

TypeScript src/browser/pw-tools-core.snapshot.ts — snapshotAiViaPlaywright 
export async function snapshotAiViaPlaywright(opts) {
  const page = await getPageForTargetId({ cdpUrl, targetId });
  ensurePageState(page);

  // 调用 Playwright 内置的 AI Snapshot 接口
  const result = await page._snapshotForAI({
    timeout: Math.max(500, Math.min(60_000, opts.timeoutMs ?? 5000)),
    track: "response",
  });
  let snapshot = String(result?.full ?? "");

  // 可选截断（防止超大页面溢出 token 预算）
  if (limit && snapshot.length > limit) {
    snapshot = `${snapshot.slice(0, limit)}\n\n[...TRUNCATED - page too large]`;
  }

  // 从 AI Snapshot 文本中提取 ref 映射
  const built = buildRoleSnapshotFromAiSnapshot(snapshot);
  storeRoleRefsForTarget({ page, cdpUrl, targetId, refs: built.refs, mode: "aria" });
  return { snapshot, refs: built.refs };
}

Role Snapshot 角色分类

Role Snapshot 将页面 DOM 按 ARIA Role 分类，并为可交互元素分配 ref ID：

角色类别 包含的 Role 是否分配 Ref
Interactive（可交互） button, link, textbox, checkbox, radio, combobox, listbox, menuitem, slider, switch, tab ... 分配 ref（如 e1, e2）
Content（内容） heading, cell, listitem, article, region, main, navigation ... 分配 ref
Structural（结构） generic, group, list, table, row, menu, toolbar, tablist, tree ... 不分配 ref（节省 token）
TypeScript src/browser/pw-role-snapshot.ts — RoleRef 类型 
export type RoleRef = {
  role: string;       // ARIA 角色（如 "button", "link"）
  name?: string;      // 可访问名称（如按钮文本）
  nth?: number;       // 同名元素的序号（用于消歧）
};

export type RoleRefMap = Record<string, RoleRef>;
// 示例: { "e1": { role: "button", name: "Submit" },
//         "e2": { role: "textbox", name: "Email" } }

两种 Refs 模式

模式 来源 定位方式 稳定性
role（默认） ariaSnapshot 解析 getByRole(role, { name }) 基于角色+名称定位，中等稳定
aria _snapshotForAI 返回 aria-ref=... 选择器 Playwright 内部 ID，跨调用自我解析更稳定
生活类比

把 Snapshot 想象成网页的文字描述： 你给一个看不见网页的朋友描述"这个页面有一个标题'登录'，一个邮箱输入框（e1）， 一个密码输入框（e2），和一个'提交'按钮（e3）"。 朋友（Agent）就可以说"请在 e1 里输入我的邮箱"。 这比发送一张截图给 Agent 看要高效得多。

Chrome Extension Relay

profile="chrome" 模式通过 Chrome Extension Relay 让 Agent 接管用户已有的 Chrome 标签页。 这是一种独特的"非侵入式"浏览器自动化——Agent 操作的是用户已经登录、已经打开的真实网页。

Chrome Extension Relay 架构
Chrome Extension（前端）
用户点击工具栏图标 attach 标签页。通过 chrome.debugger API 获取 CDP 访问。
WebSocket 连接（带认证 token）
Extension Relay Server（后端）
OpenClaw 本地 WebSocket 服务器，转发 CDP 命令/事件
CDP 命令桥接
Playwright / CDP Client
OpenClaw 的自动化引擎，通过 Relay 操控 Chrome 标签页

Relay 通信协议

Extension Relay Server 作为 CDP 代理工作，将外部 CDP 命令转发为 Chrome Extension 的 forwardCDPCommand 消息：

Relay 安全认证

安全措施 说明
Token 认证 Extension 和 Relay 共享认证 token，防止未授权连接
Loopback 绑定 Relay 默认绑定在 127.0.0.1，仅接受本地连接
用户主动 Attach 用户必须主动点击工具栏图标 attach 标签页，Agent 无法擅自接管
过期 Target 处理

Chrome Extension Relay 模式下，标签页可能在两次 Agent 调用之间被用户关闭。当 Relay 返回 404: tab not found 时，Browser Tool 会自动降级——移除 targetId 参数，使用当前活动标签页重试。这确保了 Agent 不会因为过期的 targetId 而卡住。

Wait 等待机制

浏览器自动化中，等待是最重要的可靠性保障。页面加载、AJAX 请求、动画过渡—— 都需要 Agent 在操作前确认页面已就绪。OpenClaw 通过 act:wait 动作提供 4 种等待条件：

等待条件 参数 说明 使用场景
元素选择器 selector 等待指定 CSS 选择器的元素出现在页面中 等待特定组件渲染完毕
文本消失 textGone 等待指定文本从页面中消失 等待 loading 提示消失
URL 匹配 url 等待页面 URL 匹配指定模式 等待导航完成（如登录后跳转）
加载状态 loadState 等待页面达到指定加载状态 load / domcontentloaded / networkidle
设计理念

OpenClaw 的 Browser Tool 描述中明确指出："Avoid act:wait by default; use only in exceptional cases when no reliable UI state exists."

推荐的做法是使用 snapshot 观察页面状态，然后基于 snapshot 中的 ref 进行操作。Snapshot 本身已经隐式等待了页面就绪。只在没有可靠 UI 状态指标时，才使用显式的 wait。

与 Tool 系统集成

Browser 自动化通过 createBrowserTool() 注册为一个 Agent Tool， 名称为 browser，遵循与其他工具相同的 Policy 过滤和 Hook 机制。

Tool 参数路由

browser tool 接受一个 action 参数，路由到不同的操作：

Action 功能 关键参数
status 查看浏览器状态 profile
start / stop 启动 / 停止浏览器 profile
profiles 列出可用 Profile 无
tabs 列出已打开的标签页 profile

三种 Target 模式

Browser Tool 的 target 参数控制浏览器命令发往哪个执行环境：

sandbox

发往 Docker Sandbox 内的浏览器容器。通过 sandboxBridgeUrl 连接。需要 agents.defaults.sandbox.browser.enabled=true。

host

发往宿主机上的 Browser Control Server。默认模式（无 sandbox 时）。Chrome Extension Relay 模式自动使用此 target。

node

发往远程 Node（通过 Gateway 的 node.invoke + browser.proxy 命令）。当 gateway.nodes.browser.mode=auto 且有 browser-capable node 连接时，可自动路由。

Sandbox 浏览器集成

当 Sandbox 启用浏览器支持时，OpenClaw 会创建一个独立的 Docker 容器运行 Chromium（使用 openclaw-sandbox-browser:bookworm-slim 镜像），并通过 Bridge Server 桥接：

TypeScript src/agents/sandbox/types.ts — SandboxBrowserContext 
export type SandboxBrowserContext = {
  bridgeUrl: string;       // Bridge HTTP API URL（宿主机可达）
  noVncUrl?: string;       // noVNC 观察 URL（可选）
  containerName: string;   // Docker 容器名
};

// Browser 容器与 Sandbox 容器分开运行
// Browser 容器有独立网络（openclaw-sandbox-browser）
// 以支持 Chrome 的网络访问需求
网络隔离区别

Sandbox 主容器默认 network=none（完全隔离），但 Browser 容器使用独立的 openclaw-sandbox-browser 网络——因为浏览器需要网络访问才能加载网页。两个容器的安全边界完全独立。
