消息处理模式
5-Mode 调度策略

当 Agent 正在处理一条消息时，新消息到达怎么办？OpenClaw 提供 5 种 QueueMode——steer、followup、collect、steer-backlog、interrupt——覆盖从"实时转向"到"批量合并"的全部场景。

src/auto-reply/reply/queue/types.ts 2026-03-13

问题：Agent 忙时消息怎么办

在多渠道 AI 网关中，有一个频繁出现的核心问题：

场景

用户 Alice 发了一条消息 "帮我查一下天气"，Agent 开始执行工具调用。2 秒后 Alice 又发了 "算了，帮我写一封邮件"。此时正在运行的 Agent turn 还没完成——新消息该怎么处理？

不同场景需要不同策略：

  • 实时对话（如语音）：新消息应该"打断"当前任务，立即执行。
  • 异步对话（如 Telegram）：新消息排队等待，前一轮完成后依次处理。
  • 多人群聊（如 Discord channel）：多条消息应合并为一个 prompt 批量处理，避免逐条回复。
  • 流式响应中：新消息如果是对当前话题的补充，应该"注入"到正在进行的推理流程中。

为了覆盖所有这些场景，OpenClaw 设计了 QueueMode 类型——5 种调度模式，每种对应一个策略。

TypeScript src/auto-reply/reply/queue/types.ts 
export type QueueMode =
  | "steer"          // 实时转向：注入到正在运行的 Agent
  | "followup"       // 依次跟进：排队等待，逐条执行
  | "collect"        // 批量合并：多条消息合并为一个 prompt
  | "steer-backlog"  // 混合模式：先尝试 steer，不行再 followup
  | "interrupt";     // 强制中断：清空队列，立即执行新消息

export type QueueDropPolicy = "old" | "new" | "summarize";

export type QueueSettings = {
  mode: QueueMode;
  debounceMs?: number;    // 防抖窗口（毫秒）
  cap?: number;           // 队列容量上限
  dropPolicy?: QueueDropPolicy;  // 溢出策略
};
类比

可以把 5 种 QueueMode 类比为餐厅的等位策略。steer 像加菜——直接加到正在做的菜里；followup 像叫号——依次排队等厨师做完上一桌；collect 像自助餐——多个订单合并成一盘端上来；steer-backlog 像"先试试加菜，不行就排号"；interrupt 像插队急单——当前的不做了，直接做新单。

五种 QueueMode 一览

Mode Agent 空闲时 Agent 正在运行时 Agent 正在流式输出时 典型场景
steer 立即执行 排入 followup 队列 注入到正在运行的 Agent（queueEmbeddedPiMessage） 对话型交互，用户在 Agent 思考时补充信息
followup 立即执行 排入 followup 队列，等待当前 run 完成后依次执行 同左（排队） 异步消息通道（Telegram、WhatsApp）
collect 立即执行 排入 followup 队列，排空时合并为一个 prompt 同左（合并排队） 群聊中多人连续发言，合并处理效率更高
steer-backlog 立即执行 排入 followup 队列 先尝试 steer 注入；如果注入成功且 shouldFollowup=true，仍排入 followup 需要同时响应流式中的补充和后续消息
interrupt 立即执行 清空队列 + 中止当前 run，立即执行新消息 同左（中止 + 立即执行） 语音通话模式，用户打断 Agent

collect 是全局默认模式。来看 defaultQueueModeForChannel() 的实现：

TypeScript src/auto-reply/reply/queue/settings.ts 
function defaultQueueModeForChannel(_channel?: string): QueueMode {
  return "collect";
}
为什么默认是 collect

collect 是最保守也最安全的选择——多条消息合并为一个 prompt 批量处理，既避免了重复 Agent run 的资源浪费，也保证了上下文连贯性。它的行为是：在防抖窗口（默认 1000ms）内收集所有到达的消息，然后打包成 "[Queued messages while agent was busy]" 格式的 prompt 一次性交给 Agent。

steer 模式的核心是 queueEmbeddedPiMessage()——当 Agent 正在流式输出时，新消息被直接注入到正在运行的 Pi Agent 的消息队列中，Agent 可以在下一个推理步骤"看到"这条新消息并调整输出方向。

TypeScript src/auto-reply/reply/agent-runner.ts 
// steer 模式：如果 Agent 正在流式输出，尝试注入消息
if (shouldSteer && isStreaming) {
  const steered = queueEmbeddedPiMessage(
    followupRun.run.sessionId,
    followupRun.prompt
  );
  if (steered && !shouldFollowup) {
    await touchActiveSessionEntry();
    typing.cleanup();
    return undefined;  // 注入成功，无需额外处理
  }
}

// interrupt 模式：清空队列 + 中止当前运行
if (resolvedQueue.mode === "interrupt" && laneSize > 0) {
  const cleared = clearCommandLane(sessionLaneKey);
  const aborted = abortEmbeddedPiRun(sessionIdFinal);
  logVerbose(`Interrupting ${sessionLaneKey} (cleared ${cleared}, aborted=${aborted})`);
}

TypeScript src/auto-reply/reply/queue/settings.ts 
export function resolveQueueSettings(params: ResolveQueueSettingsParams): QueueSettings {
  const channelKey = params.channel?.trim().toLowerCase();
  const queueCfg = params.cfg.messages?.queue;

  // P2: 渠道级别覆盖（如 queue.byChannel.telegram = "steer"）
  const providerModeRaw = channelKey && queueCfg?.byChannel
    ? (queueCfg.byChannel as Record<string, string | undefined>)[channelKey]
    : undefined;

  // P0 > P1 > P2 > P3 > 默认值
  const resolvedMode =
    params.inlineMode ??                            // P0: 内联指令
    normalizeQueueMode(params.sessionEntry?.queueMode) ?? // P1: 会话级别
    normalizeQueueMode(providerModeRaw) ??           // P2: 渠道级别
    normalizeQueueMode(queueCfg?.mode) ??            // P3: 全局配置
    defaultQueueModeForChannel(channelKey);           // 默认: "collect"

  // debounce 也有类似的优先级链
  const debounceRaw =
    params.inlineOptions?.debounceMs ??
    params.sessionEntry?.queueDebounceMs ??
    resolveChannelDebounce(queueCfg?.debounceMsByChannel, channelKey) ??
    resolvePluginDebounce(channelKey) ??  // 插件可声明默认 debounce
    queueCfg?.debounceMs ??
    DEFAULT_QUEUE_DEBOUNCE_MS;            // 1000ms

  return {
    mode: resolvedMode,
    debounceMs: Math.max(0, debounceRaw),
    cap: capRaw ?? DEFAULT_QUEUE_CAP,     // 20
    dropPolicy: dropRaw ?? "summarize",
  };
}

normalizeQueueMode() 负责解析用户输入的各种变体——"queue" 会被标准化为 "steer"，"coalesce" 标准化为 "collect"，"abort" 标准化为 "interrupt"：

TypeScript src/auto-reply/reply/queue/normalize.ts 
export function normalizeQueueMode(raw?: string): QueueMode | undefined {
  if (!raw) return undefined;
  const cleaned = raw.trim().toLowerCase();
  if (cleaned === "queue" || cleaned === "queued") return "steer";
  if (cleaned === "interrupt" || cleaned === "interrupts" || cleaned === "abort") return "interrupt";
  if (cleaned === "steer" || cleaned === "steering") return "steer";
  if (cleaned === "followup" || cleaned === "follow-ups") return "followup";
  if (cleaned === "collect" || cleaned === "coalesce") return "collect";
  if (cleaned === "steer+backlog" || cleaned === "steer-backlog") return "steer-backlog";
  return undefined;
}

运行时决策引擎

当一条消息到达时，系统要做一个关键决策：立即执行？排队等待？还是直接丢弃？ 这个决策由 resolveActiveRunQueueAction() 完成：

TypeScript src/auto-reply/reply/queue-policy.ts 
export type ActiveRunQueueAction = "run-now" | "enqueue-followup" | "drop";

export function resolveActiveRunQueueAction(params: {
  isActive: boolean;       // 当前会话是否有 Agent 在运行
  isHeartbeat: boolean;    // 是否为心跳消息
  shouldFollowup: boolean; // 模式是否支持 followup
  queueMode: QueueSettings["mode"];
}): ActiveRunQueueAction {
  // Case 1: 没有活跃的 Agent run -> 立即执行
  if (!params.isActive) {
    return "run-now";
  }
  // Case 2: 心跳消息在 Agent 忙时直接丢弃
  if (params.isHeartbeat) {
    return "drop";
  }
  // Case 3: followup/collect/steer-backlog/steer 模式 -> 排队
  if (params.shouldFollowup || params.queueMode === "steer") {
    return "enqueue-followup";
  }
  // Case 4: interrupt 模式 -> 立即执行（队列已在上游清空）
  return "run-now";
}

在 agent-runner.ts 中，shouldSteer 和 shouldFollowup 两个布尔值由 QueueMode 推导出来，驱动后续的分支逻辑：

TypeScript src/auto-reply/reply/get-reply-run.ts 
// 是否应该尝试 steer（实时注入）
const shouldSteer =
  resolvedQueue.mode === "steer" ||
  resolvedQueue.mode === "steer-backlog";

// 是否应该支持 followup 队列（排队等待）
const shouldFollowup =
  resolvedQueue.mode === "followup" ||
  resolvedQueue.mode === "collect" ||
  resolvedQueue.mode === "steer-backlog";

可以看到 steer-backlog 模式的独特之处——它同时设置 shouldSteer = true 和 shouldFollowup = true， 实现了"先试 steer，不行再 followup"的混合策略。

队列排空机制

当 Agent 完成一次 run 后，系统检查 followup 队列中是否有等待的消息。如果有，就启动排空循环（drain loop）。 排空行为取决于当前的 QueueMode：

Mode 排空行为 Prompt 格式
followup 逐条取出，每条独立执行一次 Agent run 原始消息文本
collect 一次取出全部，合并为一个 prompt [Queued messages while agent was busy]\n---\nQueued #1\n...\nQueued #2\n...
steer 同 followup（steer 只影响流式阶段） 原始消息文本
steer-backlog 同 followup 原始消息文本
interrupt 无排空（队列在 interrupt 时已被清空） N/A

collect 模式的排空逻辑最复杂——它需要判断是否有跨渠道消息（cross-channel items）。如果队列中的消息来自不同渠道或不同会话目标，就必须逐条处理，避免把不同上下文的消息合并到一个 prompt 中：

TypeScript src/auto-reply/reply/queue/drain.ts 
if (queue.mode === "collect") {
  // 检查是否跨渠道/跨目标
  const isCrossChannel = hasCrossChannelItems(queue.items, resolveCrossChannelKey);

  const collectDrainResult = await drainCollectQueueStep({
    collectState,
    isCrossChannel,  // 跨渠道时回退为逐条处理
    items: queue.items,
    run: runFollowup,
  });
  if (collectDrainResult === "drained") continue;

  // 合并所有消息为一个 prompt
  const prompt = buildCollectPrompt({
    title: "[Queued messages while agent was busy]",
    items,
    summary,
    renderItem: (item, idx) =>
      `---\nQueued #${idx + 1}\n${item.prompt}`.trim(),
  });
  await runFollowup({ prompt, run, enqueuedAt: Date.now(), ...routing });
}
防抖窗口

在排空之前，系统会先等待 debounceMs（默认 1000ms）的防抖窗口。这意味着用户连续快速发送的多条消息会被合并到同一批次中处理。防抖值可以通过 messages.queue.debounceMs 全局设置，也可以通过 messages.queue.debounceMsByChannel 按渠道单独调整。

与 Lane Queue 的协作

QueueMode 系统和 Lane Queue 是两个不同层次的并发控制机制，它们紧密协作：

Lane Queue（底层）

  • 保证同一会话同一时间只有一个 Agent run
  • 以 sessionKey 为 lane key
  • 纯 FIFO 排队，不关心消息语义
  • 位于 src/process/command-queue.ts

QueueMode（上层）

  • 决定如何处理 Agent 忙时到达的新消息
  • steer / followup / collect / interrupt 策略
  • 理解消息语义（合并、注入、丢弃）
  • 位于 src/auto-reply/reply/queue/
两层排队的协作关系
消息到达 → QueueMode 决策（steer / followup / collect / interrupt）
enqueue 或 run-now
Followup Queue（按 sessionKey 分桶的内存队列）
debounce 等待 → 排空 → 提交到 Lane Queue
submit
Lane Queue（保证 session 级别的串行执行）
同一 sessionKey 同一时间只有一个 Agent run

具体来说，Followup Queue 的数据结构如下：

TypeScript src/auto-reply/reply/queue/state.ts 
export type FollowupQueueState = {
  items: FollowupRun[];       // 等待执行的消息列表
  draining: boolean;           // 是否正在排空
  lastEnqueuedAt: number;      // 最近入队时间（用于防抖）
  mode: QueueMode;             // 当前模式
  debounceMs: number;          // 防抖窗口
  cap: number;                 // 容量上限
  dropPolicy: QueueDropPolicy; // 溢出策略
  droppedCount: number;        // 已丢弃消息数
  summaryLines: string[];      // 丢弃消息的摘要
  lastRun?: FollowupRun["run"]; // 最近的 run 参数（用于合并）
};

export const DEFAULT_QUEUE_DEBOUNCE_MS = 1000;
export const DEFAULT_QUEUE_CAP = 20;
export const DEFAULT_QUEUE_DROP: QueueDropPolicy = "summarize";

// 全局 Map：sessionKey -> FollowupQueueState
export const FOLLOWUP_QUEUES = new Map<string, FollowupQueueState>();

当队列容量（cap，默认 20）被用满时，dropPolicy 决定如何处理溢出：

  • "old"：丢弃最旧的消息
  • "new"：丢弃最新的消息（即拒绝入队）
  • "summarize"（默认）：丢弃最旧的消息，但保留其摘要行，排空时将摘要注入到 prompt 中

配置与调优

QueueMode 系统的所有参数都可以通过 openclaw.yaml 配置文件调整：

yaml ~/.openclaw/config.yaml 
messages:
  queue:
    # 全局默认模式（默认: collect）
    mode: collect

    # 按渠道覆盖模式
    byChannel:
      telegram: steer        # Telegram 用 steer（支持流式注入）
      discord: collect        # Discord 用 collect（群聊合并）
      signal: followup        # Signal 逐条处理
      webchat: interrupt      # 语音通话用 interrupt

    # 全局防抖窗口（默认: 1000ms）
    debounceMs: 1000

    # 按渠道覆盖防抖
    debounceMsByChannel:
      telegram: 500           # Telegram 更快响应
      discord: 2000           # Discord 群聊多等一会儿

    # 队列容量上限（默认: 20）
    cap: 20

    # 溢出策略（默认: summarize）
    drop: summarize

除了配置文件，用户还可以通过内联指令在消息中临时切换模式：

指令 效果 作用范围
/queue steer切换到 steer 模式当前会话持久
/queue collect切换到 collect 模式当前会话持久
/queue followup切换到 followup 模式当前会话持久
/queue interrupt切换到 interrupt 模式当前会话持久
/queue steer-backlog切换到 steer-backlog 模式当前会话持久

内联指令会写入 sessionEntry.queueMode，在解析优先级链中位于 P1（仅次于 P0 的单条消息覆盖），优先于渠道级别和全局配置。

插件默认 debounce

渠道插件可以通过 ChannelPlugin.defaults.queue.debounceMs 声明自己的默认防抖值。这在解析链中位于渠道配置和全局配置之间——如果用户没有显式设置，就使用插件的推荐值。例如，一个 webhook 渠道可能推荐较长的 debounce（如 3000ms）来应对批量推送。
