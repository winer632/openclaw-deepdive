多 Agent 与 Canvas
Multi-Agent Isolation & A2UI

OpenClaw 支持在单个 Gateway 进程内运行多个完全隔离的 Agent，每个 Agent 拥有独立的工作区、认证、会话和工具集。 Canvas 系统通过 A2UI 格式让 Agent 生成可交互的实时 UI。

src/agents/, src/canvas-host/ 2026-03-13 商汤科技 亚太业务事业群 · 王欣鑫

Agent 隔离维度

OpenClaw 中的"Agent"不是一个简单的提示词模板，而是一个完全隔离的 AI 大脑。 每个 Agent 在六个维度上实现了严格的边界隔离：

隔离维度 隔离方式 存储位置
工作区 (Workspace) 每个 Agent 独立的文件目录，包含 SOUL.md、AGENTS.md、HEARTBEAT.md 等 ~/.openclaw/workspace-<agentId>
认证 (Auth) 每个 Agent 独立的 auth-profiles.json，模型 API 密钥不共享 ~/.openclaw/agents/<agentId>/agent/
会话 (Session) 独立的会话存储，Session Key 按 agent:<id>:<key> 命名空间隔离 ~/.openclaw/agents/<agentId>/sessions/
工具 (Tools) 工具集可按 Agent 独立配置（启用/禁用特定工具） config: agents.list[].tools
模型 (Model) 每个 Agent 可指定不同的模型、fallback 链和 thinking 级别 config: agents.list[].model
技能 (Skills) Agent 工作区的 skills/ 目录 + 共享 ~/.openclaw/skills 文件系统层面隔离
重要约束

永远不要在不同 Agent 之间复用 agentDir——这会导致认证和会话冲突。 如果需要共享凭据，应该将 auth-profiles.json 复制到目标 Agent 的 agentDir 中。

类比

每个 Agent 就像办公楼里的一间独立办公室：有自己的文件柜（工作区）、门禁卡（认证）、 日程表（会话）、工具箱（工具集）。办公室之间不共享文件柜钥匙，但大楼管理系统（Gateway） 统一调度它们何时处理来访者的消息。

Per-Agent 配置覆盖机制

OpenClaw 使用三层配置合并策略：全局默认 → Agent 默认 → 每个 Agent 的个性化覆盖。

TypeScript src/agents/agent-scope.ts — 配置解析类型 
type ResolvedAgentConfig = {
  name?: string;
  workspace?: string;         // 独立工作区路径
  agentDir?: string;          // 独立状态目录
  model?: AgentEntry["model"];         // 模型覆盖
  skills?: AgentEntry["skills"];       // 技能过滤器
  heartbeat?: AgentEntry["heartbeat"]; // 心跳配置覆盖
  identity?: AgentEntry["identity"];   // 身份配置
  subagents?: AgentEntry["subagents"]; // 子 Agent 策略
  sandbox?: AgentEntry["sandbox"];     // 沙箱模式
  tools?: AgentEntry["tools"];         // 工具集覆盖
};

配置合并的优先级链：

配置合并优先级（从低到高）
系统硬编码默认值
DEFAULT_AGENT_ID = "main"
DEFAULT_HEARTBEAT_EVERY = "30m"
被 agents.defaults 覆盖
agents.defaults
所有 Agent 的共享默认值（心跳、模型、沙箱等）
被 agents.list[].* 覆盖
agents.list[i].*
每个 Agent 的个性化配置（最高优先级）

以心跳配置为例，resolveHeartbeatConfig 函数先读取 agents.defaults.heartbeat， 再用目标 Agent 的 agents.list[].heartbeat 进行展开覆盖（{ ...defaults, ...overrides }）。 这意味着 Agent 只需声明想要修改的字段，其余继承默认值。

多 Agent 模式

OpenClaw 支持两种截然不同的多 Agent 使用模式，适用于不同的场景：

模式一：并行隔离 Agent

在 agents.list 中定义多个顶层 Agent，每个 Agent 通过 bindings 绑定到不同的消息通道或账户。 这是"多人格助手"模式——同一个 Gateway 运行多个完全独立的 AI 人格。

并行隔离 Agent 模式
agent:coding
WA
TG
绑定 WhatsApp + Telegram 账号 A
agent:social
DC
SL
绑定 Discord + Slack 账号 B
agent:work
TG
绑定 Telegram 账号 C（不同 bot）

模式二：动态子 Agent 派生

主 Agent 在运行过程中可以通过 sessions_spawn 工具动态创建子 Agent。 子 Agent 在独立的会话中执行任务，完成后将结果"announce"回父 Agent。 这是"分工协作"模式。

TypeScript src/agents/subagent-spawn.ts — 派生参数 
export type SpawnSubagentParams = {
  task: string;               // 任务描述
  label?: string;             // 显示标签
  agentId?: string;           // 目标 Agent（可选，跨 Agent 派生）
  model?: string;             // 模型覆盖
  thinking?: string;          // 推理级别（low / medium / high）
  runTimeoutSeconds?: number; // 执行超时
  mode?: "run" | "session";   // run=一次性执行 / session=持久会话
  cleanup?: "delete" | "keep"; // 完成后是否清理会话
  sandbox?: "inherit" | "require"; // 沙箱模式
  attachments?: Array<{       // 传递给子 Agent 的文件附件
    name: string;
    content: string;
    encoding?: "utf8" | "base64";
  }>;
};
派生模式 生命周期 适用场景
run 执行一次任务后自动结束，可选清理会话数据 一次性计算、文件处理、代码执行
session 创建持久会话，绑定到消息线程，持续对话 长期跟踪任务、多轮对话、项目管理

深度限制

子 Agent 可以递归派生更深层的子 Agent，但受到最大深度限制 （DEFAULT_SUBAGENT_MAX_SPAWN_DEPTH）的保护。这防止了无限递归的 Agent 链。

子 Agent 通信模型

父子 Agent 之间的通信采用异步推送模型（push-based），而非轮询。 这是 OpenClaw 子 Agent 系统最精妙的设计之一。

核心设计

Auto-announce 是推送模型。父 Agent 在派生子 Agent 后，不应轮询（不调用 sessions_list、sessions_history 或 exec sleep）。 子 Agent 完成后，结果会作为"用户消息"自动推送到父 Agent 的会话中。

子 Agent 通信时序
父 Agent 调用 sessions_spawn
task="分析这份报告"，mode="run"
立即返回 childSessionKey
子 Agent 在 subagent 车道执行
独立会话、独立上下文、并发上限 8
执行完毕触发 announce
结果推送到父 Agent 会话
captureSubagentCompletionReply → runSubagentAnnounceFlow

Announce 可靠性机制

  • 超时控制（SUBAGENT_ANNOUNCE_TIMEOUT_MS = 120s）—— 防止 announce 无限等待
  • 指数退避重试（1~8 秒）—— 处理父 Agent 暂时繁忙的情况
  • 最大重试次数（MAX_ANNOUNCE_RETRY_COUNT = 3）—— 防止无限重试循环
  • 持久化恢复（persistSubagentRunsToDisk）—— Gateway 重启后恢复 subagent 运行状态

SubagentRunRecord 注册表

所有活跃的子 Agent 运行通过 subagentRuns: Map<string, SubagentRunRecord> 在进程内追踪。 注册表支持查询活跃后代计数、检测循环引用、管理 announce 队列等操作。

Canvas / A2UI 技术栈

Canvas 是 OpenClaw 的可视化输出层——让 Agent 不仅能输出文本， 还能生成和控制一个实时渲染的交互式 UI。A2UI（Agent-to-UI）是 Canvas 的底层数据格式。

A2UI v0.8 格式

A2UI 使用 JSONL（JSON Lines） 格式，每行是一个 UI 指令。 Agent 通过 canvas 工具的 a2ui_push action 向 Canvas 推送 UI 更新。

TypeScript src/agents/tools/canvas-tool.ts — Canvas 工具 Action 列表 
const CANVAS_ACTIONS = [
  "present",     // 展示 Canvas 窗口
  "hide",        // 隐藏 Canvas 窗口
  "navigate",    // 导航到指定 URL
  "eval",        // 在 Canvas WebView 中执行 JavaScript
  "snapshot",    // 截取 Canvas 屏幕截图
  "a2ui_push",   // 推送 A2UI JSONL 数据更新 UI
  "a2ui_reset",  // 重置 A2UI 状态
] as const;

跨平台渲染架构

Canvas 的渲染基于 WebView，在所有平台上使用统一的 HTML/JS 渲染引擎：

平台 渲染组件 通信桥
macOS WKWebView（SwiftUI） Gateway HTTP 服务
iOS WKWebView window.webkit.messageHandlers.openclawCanvasA2UIAction
Android Android WebView window.openclawCanvasA2UIAction.postMessage()
浏览器 原生浏览器 WebSocket（/__openclaw__/ws）
设计决策

A2UI 的跨平台桥接代码非常精巧：在运行时检测平台（iOS webkit handler、Android bridge、浏览器 WebSocket）， 自动选择正确的通信通道。Agent 调用的 canvas 工具接口在所有平台上完全一致。

Canvas 工作流

从 Agent 生成 UI 到用户看到渲染结果，Canvas 经历三个阶段：

Canvas 三阶段工作流：Parse → Push → Render
1. Parse（解析）
Agent 生成 A2UI JSONL 内容
canvas tool 验证格式、检查路径安全
通过 Gateway RPC
2. Push（推送）
node.invoke 将 a2ui_push 发送到目标 Node
Node 的 WebView 接收 JSONL 数据
WebView 注入
3. Render（渲染）
A2UI 运行时解析 JSONL，动态渲染 UI
用户交互通过 sendUserAction() 回传

A2UI 静态资源

A2UI 渲染引擎是一组预编译的静态资源（index.html + a2ui.bundle.js）， 通过 Gateway 的 HTTP 服务提供（路径：/__openclaw__/a2ui）。 系统支持多种候选路径来定位这些资源，适配 source、dist、launchd 等不同运行环境。

用户交互回传

Canvas 不是单向输出——用户可以在 UI 上进行交互，交互事件通过统一的 sendUserAction() 接口回传到 Agent。这实现了 Agent 与用户之间的双向 UI 通信。

TypeScript src/canvas-host/a2ui.ts — 跨平台交互桥 
// 统一的跨平台 action 发送接口
function sendUserAction(userAction) {
  const id = userAction?.id?.trim() ||
    globalThis.crypto?.randomUUID?.() || String(Date.now());
  const action = { ...userAction, id };
  return postToNode({ userAction: action });
}

// 自动检测平台并选择通信通道
function postToNode(payload) {
  const raw = typeof payload === "string" ? payload : JSON.stringify(payload);
  // iOS: webkit messageHandlers
  const iosHandler = globalThis.webkit?.messageHandlers?.openclawCanvasA2UIAction;
  if (iosHandler) { iosHandler.postMessage(raw); return true; }
  // Android: JS bridge
  const androidHandler = globalThis.openclawCanvasA2UIAction;
  if (androidHandler) { androidHandler.postMessage(raw); return true; }
  return false;
}

WebSocket UI 更新机制

在浏览器端，Canvas 通过 WebSocket 接收实时更新。 Gateway 在 /__openclaw__/ws 路径上提供 WebSocket 端点， Canvas HTML 页面加载时自动建立连接。

TypeScript src/canvas-host/a2ui.ts — Live Reload 注入 
// 在所有 HTML 响应的 </body> 前自动注入 WebSocket 连接
const ws = new WebSocket(
  proto + "://" + location.host + "/__openclaw__/ws" + capQuery
);
ws.onmessage = (ev) => {
  if (String(ev.data || "") === "reload") location.reload();
};

这个机制实现了多个重要功能：

  • 实时 UI 刷新：当 Agent 推送新的 A2UI 数据时，WebSocket 发送 "reload" 消息触发页面刷新
  • 能力令牌传递：通过 URL 参数 oc_cap 传递 canvas capability token，实现安全的访问控制
  • 自动重连：浏览器端 WebSocket 断连后，页面刷新会自动重新建立连接

Canvas Capability Token

每个 Canvas 会话都有一个带时效的 capability token（CANVAS_CAPABILITY_TTL_MS）， 通过 mintCanvasCapabilityToken() 生成。Token 确保只有授权的 Node 能访问 Canvas 内容， 防止未配对设备窥探 Agent 的 UI 输出。
