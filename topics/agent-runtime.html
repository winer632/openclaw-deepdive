Agent Runtime 选型
Build vs Buy 的五种答案

你的 Agent 循环应该自己写，还是用现成的？从 Claude SDK 的黑盒运行时到 LangGraph 的图状态机，再到 Rust 自建的企业级执行器，五个项目给出了五种截然不同的回答。

跨项目对比分析 2026-03-13 商汤科技 亚太业务事业群 · 王欣鑫

核心问题

构建一个 AI Agent 应用时，执行引擎（Agent Runtime）是最关键的基础设施决策之一。 它决定了 Agent 如何调用 LLM、如何执行工具、如何管理上下文——以及你对这些行为有多少控制权。

我们对比了五个项目，它们面对同一个问题给出了截然不同的答案：

Agent Runtime 设计光谱
Claude SDK nanoclaw · TS
LangGraph Python
Pi Agent TypeScript
picoclaw Go
IronClaw Rust
黑盒 · 零定制 · 快速上线 白盒 · 全定制 · 企业级
核心洞察

这不是"谁更好"的问题，而是"你需要多少控制权"的问题。五个项目的选择背后，是对 Provider 数量、安全隔离、定制深度、部署约束的不同取舍。

Pi Agent Core 全貌

Pi Agent 是一个完整的 AI Agent 框架（monorepo，7 个包），由 @mariozechner 开发， 为 OpenClaw 提供了底层的 Agent 能力。理解 Pi Agent 的全貌，才能理解 OpenClaw 为什么只用了其中一部分。

核心循环

Pi Agent Core 的 agentLoop() 是整个框架的心脏：

TypeScript pi-mono/packages/agent/src/agent-loop.ts 
// 简化后的核心循环
async function agentLoop(config) {
  emit("agent_start");

  while (true) {
    emit("turn_start");

    // 1. 消息变换管线
    const messages = await config.transformContext(allMessages);
    const llmMessages = await config.convertToLlm(messages);

    // 2. 流式调用 LLM
    const response = await streamFn(model, llmMessages, options);

    // 3. 工具执行（支持 Steering 中断）
    if (response.toolCalls) {
      for (const call of response.toolCalls) {
        const result = await tool.execute(call);
        // 检查是否有 Steering 消息打断
        const steering = await config.getSteeringMessages?.();
        if (steering.length > 0) break; // 中断剩余工具
      }
    }

    emit("turn_end");

    // 4. 检查 Follow-up 消息
    if (!hasToolCalls && !followUps.length) break;
  }

  emit("agent_end");
}
设计哲学

Pi Agent 的哲学是"极简核心 + 扩展机制"——不内置 MCP、不内置子 Agent、不内置权限弹窗、不内置 Plan 模式。这些能力全部留给使用者通过扩展系统自行构建。

OpenClaw 的选择：框架 vs 库

OpenClaw 面对 Pi Agent 的完整"整车方案"，做了一个明确的架构决策： 把 Pi Agent 当"库"用，而不是当"框架"用。

用了什么

pi-ai · streamSimple() pi-ai · 消息类型 pi-agent-core · 类型定义 pi-coding-agent · SessionManager pi-coding-agent · 编码工具 pi-coding-agent · ExtensionFactory

没有用什么

pi-agent-core · Agent 类 pi-agent-core · agentLoop() pi-coding-agent · AgentSession pi-coding-agent · CLI pi-tui · 终端 UI pi-mom / pi-web-ui / pi-pods

为什么不用"整车方案"

根本原因：Pi Agent 是为单用户单模型的终端编码助手设计的，OpenClaw 是多通道多用户多模型的 AI 网关。

需求维度 Pi Agent 假设 OpenClaw 需要
模型 单模型 + 单认证 多模型 Failover + Auth Profile 轮换
用户 单用户（终端操作者） 多用户，按用户/通道区分工具权限
工具执行 直接操作宿主文件系统 Docker 容器沙箱 + 按会话隔离进程
输出目标 单终端 Web / Gateway / Mobile 多表面推送
Provider 特异性 由 pi-ai 统一处理 需要逐一 patch（Gemini 消息序列、XAI 编码等）
上下文压缩 基础开关式 摘要质量校验 + Cache TTL 感知裁剪
类比

Pi Agent 之于 OpenClaw，更像是"引擎零件"而非"整车方案"。 OpenClaw 取用了 Pi Agent 最成熟的零件（LLM 调用层 + 会话持久化 + 编码工具）， 然后在其之上自建了多通道调度、权限控制、沙箱隔离等上层系统。

Claude Agent SDK vs Pi Agent Core

这两者代表了 Agent Runtime 设计的两个极端：黑盒运行时 vs 白盒框架。

Claude Agent SDK

黑盒 — 调用 query() 即获得完整的 Agent 循环、工具执行、Session 管理。开发者不需要（也无法）控制内部行为。

只能通过 allowedTools、hooks、systemPrompt 进行有限配置。

Pi Agent Core

白盒 — 提供 Agent 类和 agentLoop()，但 transformContext、convertToLlm、streamFn 全部可替换。

三阶段消息管线完全开放，开发者对每一步都有完全控制权。

维度 Claude Agent SDK Pi Agent Core
Provider 支持 仅 Claude（Anthropic） 24+ Provider
工具体系 内置 Claude Code 全套（Bash/Read/Write/Edit…） 内置编码工具 + ExtensionFactory
控制粒度 低 — hooks + allowedTools 高 — 消息管线每步可替换
消息管线 不可见 AgentMessage → transform → convert → LLM
上手速度 极快 — 一个 query() 调用 中等 — 需要理解三层架构
供应商锁定 强 — 绑定 Anthropic 无 — 可接任何 Provider
选型陷阱

Claude SDK 的"简单"是有代价的——当你需要多 Provider 切换、自定义工具执行策略、或白盒控制 Agent 行为时，SDK 的黑盒特性会成为阻碍。选型时需要评估：你当前的"简单"需求，是否会在产品演进中变成"锁定"风险？

适用场景分析

Pi Agent Core

可嵌入的多 Provider Agent 引擎

  • 需要深度定制 Agent 行为的产品
  • 需要多 LLM 提供商支持
  • 浏览器/移动端嵌入（via streamProxy）

Claude SDK (nanoclaw)

开箱即用的 Claude Agent 运行时

  • Claude 为唯一模型，快速上线
  • 不需要自定义执行循环
  • 注重容器隔离安全性

picoclaw (Go)

极致轻量的嵌入式 Agent

  • 资源受限设备（树莓派、IoT、<10MB RAM）
  • Go 生态集成
  • 大量 MCP 工具时的 TTL 发现机制

IronClaw (Rust)

生产级高安全 Agent 平台

  • WASM 沙箱 + prompt injection 防御
  • 工具审批流 + 成本护栏
  • 企业级部署（PostgreSQL 持久化）

LangGraph (Python / TypeScript)

图状态机 Agent 框架 · LangChain 生态

  • 需要可视化调试和 Checkpoint 时间旅行
  • Human-in-the-Loop 审批是核心需求
  • 复杂多 Agent 协调（Supervisor / 层级团队）
  • 已在 LangChain 生态中，希望声明式定义 Agent 流程

设计启示

五个执行器的对比揭示了一个清晰的选型框架—— Agent Runtime 的设计决策本质上是在三个维度上做取舍：

取舍维度 选 Buy（SDK） 选 Build（自建）
Provider 锁定 可接受单一 Provider 需要多 Provider 或可能迁移
行为控制 默认行为已满足需求 需要自定义工具策略、审批流、安全策略
上市速度 快速验证优先 长期产品，愿意投入基础设施
最终总结

Claude SDK（黑盒，零定制）→ LangGraph（图状态机，声明式）→ Pi Agent Core（白盒，多 Provider + 可嵌入）→ picoclaw（白盒，极轻量 + 并行）→ IronClaw（白盒，安全 + 企业级）

没有"最好"的 Agent Runtime，只有最匹配你场景的。选型的核心问题永远是：你需要多少控制权？
