存储架构总览

类比 把 Memory 系统想象成一座个人图书馆：Markdown 文件是书架上的笔记本（人类可读、可直接编辑）；SQLite 数据库是馆员的索引卡片柜（结构化、可高速检索）；Embedding 向量是每一页内容的"语义指纹"，让馆员无需逐页翻阅就能找到最相关的段落。

OpenClaw 的记忆系统采用了双层存储架构—Markdown 文件是用户可读、可编辑的事实源（source of truth）， SQLite 数据库则是纯粹的索引加速层。这个设计决策让记忆数据始终保持透明和可移植。

SQLite Schema

索引数据库包含四张核心表和两个虚拟/扩展表：

SQL src/memory/memory-schema.ts — 核心表结构 
// files 表 — 跟踪每个 Markdown 文件的哈希和修改时间
CREATE TABLE files (
  path TEXT PRIMARY KEY,
  source TEXT NOT NULL DEFAULT 'memory',  -- 'memory' | 'sessions'
  hash TEXT NOT NULL,
  mtime INTEGER NOT NULL,
  size INTEGER NOT NULL
);

// chunks 表 — 存储分块后的文本和嵌入向量
CREATE TABLE chunks (
  id TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  source TEXT NOT NULL DEFAULT 'memory',
  start_line INTEGER NOT NULL,
  end_line INTEGER NOT NULL,
  hash TEXT NOT NULL,
  model TEXT NOT NULL,        -- 生成嵌入时使用的模型
  text TEXT NOT NULL,         -- 分块文本内容
  embedding TEXT NOT NULL,    -- 向量嵌入（JSON 数组）
  updated_at INTEGER NOT NULL
);

// embedding_cache — 避免对相同文本重复调用 Embedding API
// chunks_fts — FTS5 虚拟表，全文关键词搜索（BM25 排名）
// chunks_vec — sqlite-vec 扩展表，向量近邻搜索
设计原则

Markdown 文件永远是事实源—SQLite 数据库可以随时删除并重建。用户直接编辑 MEMORY.md 即可更新记忆，无需学习任何 API。这让记忆数据天然具备可读性（纯文本）、可版本控制（Git 友好）和可迁移性（复制文件即可）。

索引管线

当 Markdown 文件发生变更时，索引管线会将文件内容切分为小块（chunks），为每个块生成嵌入向量， 然后写入 SQLite 数据库。整个过程是增量式的—只有变更的文件会被重新索引。

分块策略：400-token + 80-token 滑动窗口

TypeScript src/agents/memory-search.ts — 默认分块参数 
const DEFAULT_CHUNK_TOKENS = 400;     // 每个块最大 400 tokens
const DEFAULT_CHUNK_OVERLAP = 80;     // 相邻块重叠 80 tokens（滑动窗口）

Markdown 文件按行遍历，当累积文本超过 token 限制时产生一个新块。相邻块之间有 重叠区域，确保跨越块边界的信息不会丢失。如果某个块超过了 Embedding 模型的输入上限， enforceEmbeddingMaxInputTokens 会以 UTF-8 字节长度为保守上界进行二次分割。

UTF-8 字节估算

使用 UTF-8 字节数作为 token 数的保守估计（每个 token 至少占 1 字节），避免了对不同分词器的硬依赖，同时保证不会超过模型的输入限制。二次分割还会检测 surrogate pair 避免在 Unicode 代理对中间切断。

增量索引

同步过程是增量式的：每个文件通过 hash + mtime 跟踪变更状态。嵌入缓存表 embedding_cache 以 (provider, model, provider_key, hash) 为联合主键，即使全量重建索引时也能复用已有的向量。只读数据库异常时还有自动恢复机制（重新打开连接并重试）。

TypeScript src/memory/embeddings.ts — auto 模式核心逻辑 
if (requestedProvider === "auto") {
  // 1. 尝试本地模型（仅当 GGUF 文件存在时）
  if (canAutoSelectLocal(options)) {
    try { return await createProvider("local"); }
    catch (err) { localError = formatLocalSetupError(err); }
  }
  // 2. 依次尝试远程 Provider
  for (const provider of REMOTE_EMBEDDING_PROVIDER_IDS) {
    try {
      const result = await createProvider(provider);
      return { ...result, requestedProvider };
    } catch (err) {
      if (isMissingApiKeyError(err)) {
        missingKeyErrors.push(message);
        continue;  // API Key 缺失 → 跳过，尝试下一个
      }
      throw err;   // 网络错误 → 致命，立即中止
    }
  }
  // 3. 全部失败 → 返回 null provider（FTS-only 降级）
  return { provider: null, requestedProvider,
           providerUnavailableReason: reason };
}
Ollama 排除

Ollama 被有意排除在 auto 模式之外（REMOTE_EMBEDDING_PROVIDER_IDS 不包含 "ollama"），因为 auto 模式不应隐式假设本地有 Ollama 实例运行。需要使用 Ollama 时必须显式设置 provider: "ollama"。

Fallback 与向量归一化

当显式指定的 Provider 失败时，可通过 fallback 配置备用 Provider（如 provider: "openai", fallback: "local"）。所有 Embedding 结果存储前都经过 sanitizeAndNormalizeEmbedding：将非有限数替换为 0 并做 L2 归一化，确保不同 Provider 的向量在余弦相似度计算中具有可比性。

双路混合搜索

Memory 系统的搜索引擎由 manager-search.ts 实现，包含两条独立的检索路径，通过加权融合产生最终结果。

Vector 语义检索

  • 基于 sqlite-vec 扩展的 vec_distance_cosine 函数
  • 适合模糊语义查询，如"之前讨论过的 API 设计方案"
  • 需要 Embedding Provider 可用
  • 退化方案：无 sqlite-vec 时用纯 JS 余弦相似度逐条计算

FTS5 关键词检索

  • 基于 SQLite FTS5 的 BM25 算法排名
  • 适合精确关键词匹配，如人名、日期、项目代号
  • 不依赖任何外部服务或 API
  • 当 Embedding 完全不可用时，自动切换为 FTS-only 模式
TypeScript src/memory/manager-search.ts — Vector 检索核心 SQL 
// sqlite-vec 方案：在 C 扩展中直接计算余弦距离
const rows = params.db.prepare(
  `SELECT c.id, c.path, c.start_line, c.end_line, c.text,
          c.source,
          vec_distance_cosine(v.embedding, ?) AS dist
     FROM ${params.vectorTable} v
     JOIN chunks c ON c.id = v.id
    WHERE c.model = ?${params.sourceFilterVec.sql}
    ORDER BY dist ASC
    LIMIT ?`
).all(vectorToBlob(params.queryVec), params.providerModel, ...);

// score = 1 - dist（距离越小，相似度越高）
return rows.map(row => ({ ...row, score: 1 - row.dist }));
优雅降级

当 sqlite-vec 扩展不可用时，系统回退到纯 JavaScript 实现：从 chunks 表加载所有向量文本，用 cosineSimilarity 逐一计算相似度。性能较低但功能等价，确保了跨平台兼容性。当 status() 返回 vector.available: false 时即表示使用了 JS 回退方案。

FTS-only 降级模式

当没有任何 Embedding Provider 可用时（provider === null），系统进入 FTS-only 模式。此时会先用 extractKeywords() 从自然语言查询中提取关键词（如 "that thing we discussed about the API" 提取为 ["discussed", "API"]），分别搜索后合并去重，保留最高分。status().custom.searchMode 会返回 "fts-only"。

Hybrid 融合与高级排序

当两条检索路径都返回结果时，mergeHybridResults 将它们融合为一个统一的排序列表。

Hybrid 融合公式
  finalScore = vectorWeight * vectorScore + textWeight * textScore
  默认: finalScore = 0.7 * cosine_sim + 0.3 * bm25_normalized
参数默认值说明
hybrid.vectorWeight0.7向量相似度在融合评分中的权重
hybrid.textWeight0.3关键词匹配在融合评分中的权重
query.maxResults6返回的最大结果数
query.minScore0.35最低相关性阈值
candidateMultiplier4每条路径返回 maxResults * 4 个候选再合并

mmr.lambda0.7相关性与多样性的平衡系数
temporalDecay.enabledfalse时间衰减：越近的记忆权重越高
temporalDecay.halfLifeDays30时间衰减半衰期（天）
minScore 边界处理

当所有结果因 minScore 被过滤但存在 keyword 命中时，系统会放宽阈值至 Math.min(minScore, textWeight)。这解决了一个微妙的边界问题：关键词精确匹配的最高得分等于 textWeight（如 0.3），如果 minScore 设为 0.35 则精确匹配会被错误过滤。

安全护栏

Memory Flush 的 prompt 中通过 ensureMemoryFlushSafetyHints 强制注入三条安全提示，即使用户自定义了 prompt 也会被追加：

MEMORY.md / SOUL.md / TOOLS.md / AGENTS.md 等为只读 保护引导文件不被 Flush 修改
Flush 与 Compaction 的关系

Memory Flush 发生在 Compaction 之前。上下文即将被压缩时，先让 Agent 把重要信息写到磁盘，然后 Compaction 再安全地压缩上下文。如果 Flush 本身触发了 Compaction（因为写入操作增加了 token 数），系统通过 incrementCompactionCount 更新计数器并在 memoryFlushCompactionCount 中记录，防止下一轮重复触发。

Agent 工具接口

记忆系统通过两个 Agent Tool 暴露给 AI 模型，遵循"先搜索，后精读"的两步模式：

memory_search

语义搜索—输入自然语言查询，返回最相关的记忆片段。 工具描述明确标注为 "Mandatory recall step"，提示 Agent 在回答涉及历史决策、人物、偏好等问题前必须先调用。

参数: query, maxResults?, minScore?

memory_get

精确读取—根据 path + 行号范围读取原始 Markdown 内容。通常在 memory_search 之后使用，拉取完整上下文。内置路径安全检查：只允许读取 memory 目录及 extraPaths。

参数: path, from?, lines?

TypeScript src/memory/types.ts — MemorySearchResult 
type MemorySearchResult = {
  path: string;        // 相对路径，如 "memory/2026-03-10.md"
  startLine: number;   // 片段起始行
  endLine: number;     // 片段结束行
  score: number;       // 相似度分数 (0-1)
  snippet: string;     // 文本片段（最多 700 字符）
  source: "memory" | "sessions";
  citation?: string;   // 如 "memory/2026-03-10.md#L42-L58"
};

Citations 模式

搜索结果的引用标注支持三种模式："auto"（默认，私聊显示、群聊隐藏）、"on"（始终显示）、"off"（始终隐藏）。引用格式为 path#Lstart-Lend，让 Agent 在回复中标注信息来源。聊天类型通过解析 sessionKey 中的 :group: 或 :channel: 标记自动判断。

两步模式类比 memory_search 相当于在图书馆的检索系统中搜索关键词，得到一组书名和页码。memory_get 则是根据这些页码翻开具体的书页阅读内容。先检索再精读，避免一次性注入过多上下文。

架构总结

Memory 系统的精妙之处在于它的层层降级设计：有 sqlite-vec 就用硬件加速向量搜索，没有就用纯 JS 余弦计算；有 Embedding API 就做语义搜索，没有就退回 FTS5 关键词匹配；有预压缩空间就做 Memory Flush，没有就正常 Compaction。无论运行环境多么受限，Agent 总能从记忆中检索信息。这种"尽力而为但永不崩溃"的哲学，贯穿了整个系统的设计。
