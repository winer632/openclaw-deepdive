渠道全景：从 9 到 40+

OpenClaw 的核心使命是做一个多渠道 AI 网关——用户在任何一个消息平台上发消息，背后都由同一个 Agent 引擎处理。 为了实现这个目标，OpenClaw 将渠道分为两大类：内置渠道（Core Channels）和扩展渠道（Extension Channels）。

类型 渠道列表 代码位置
内置渠道 (9) Telegram, WhatsApp, Discord, IRC, Google Chat, Slack, Signal, iMessage, LINE src/telegram/, src/discord/, src/slack/, src/signal/, src/imessage/, src/web/ (WhatsApp)
扩展渠道 (30+) MS Teams, Matrix, Mattermost, Feishu, Nostr, Zalo, Twitch, Synology Chat, Nextcloud Talk, BlueBubbles, Tlon, Voice Call ... extensions/msteams/, extensions/matrix/, extensions/feishu/ 等

内置渠道在 src/channels/registry.ts 中通过 CHAT_CHANNEL_ORDER 硬编码排序，而扩展渠道通过 Plugin SDK 的 api.registerChannel() 动态注册。 两类渠道共享完全相同的 ChannelPlugin 接口——对 Agent 引擎来说，它们没有区别。

TypeScript src/channels/registry.ts 
export const CHAT_CHANNEL_ORDER = [
  "telegram",
  "whatsapp",
  "discord",
  "irc",
  "googlechat",
  "slack",
  "signal",
  "imessage",
  "line",
] as const;

export type ChatChannelId = (typeof CHAT_CHANNEL_ORDER)[number];
设计洞察

内置渠道与扩展渠道的唯一区别是代码位置——内置在 src/，扩展在 extensions/。它们都实现同一个 ChannelPlugin 接口，都通过同一套 Plugin Registry 被发现和加载。这意味着任何扩展渠道都可以在不修改核心代码的情况下，获得与内置渠道完全相同的能力。

ChannelPlugin 核心接口

每个渠道（无论内置还是扩展）都必须实现 ChannelPlugin 接口。这个接口定义在 src/channels/plugins/types.plugin.ts 中， 是整个渠道系统的契约（contract）。来看它的完整结构：

TypeScript src/channels/plugins/types.plugin.ts 
export type ChannelPlugin<ResolvedAccount = any, Probe = unknown, Audit = unknown> = {
  id: ChannelId;
  meta: ChannelMeta;
  capabilities: ChannelCapabilities;
  defaults?: {
    queue?: { debounceMs?: number };
  };
  reload?: { configPrefixes: string[]; noopPrefixes?: string[] };

  // === 核心适配器 ===
  onboarding?: ChannelOnboardingAdapter;     // CLI 引导向导
  config: ChannelConfigAdapter<ResolvedAccount>; // 配置读取（必选）
  configSchema?: ChannelConfigSchema;        // JSON Schema
  setup?: ChannelSetupAdapter;               // 账户设置
  pairing?: ChannelPairingAdapter;           // 配对 / 授权
  security?: ChannelSecurityAdapter;         // DM 安全策略
  groups?: ChannelGroupAdapter;              // 群组策略
  mentions?: ChannelMentionAdapter;          // @提及处理
  outbound?: ChannelOutboundAdapter;         // 出站消息
  status?: ChannelStatusAdapter;             // 状态 / 探活
  gateway?: ChannelGatewayAdapter;           // Gateway 生命周期
  auth?: ChannelAuthAdapter;                 // 登录认证
  elevated?: ChannelElevatedAdapter;         // 提权控制
  commands?: ChannelCommandAdapter;          // 命令控制
  streaming?: ChannelStreamingAdapter;       // 流式回复
  threading?: ChannelThreadingAdapter;       // 线程/话题
  messaging?: ChannelMessagingAdapter;       // 目标解析
  agentPrompt?: ChannelAgentPromptAdapter;   // Agent 提示词
  directory?: ChannelDirectoryAdapter;       // 联系人目录
  resolver?: ChannelResolverAdapter;         // 目标名解析
  actions?: ChannelMessageActionAdapter;     // 消息动作（按钮等）
  heartbeat?: ChannelHeartbeatAdapter;       // 心跳检查
  agentTools?: ChannelAgentToolFactory | ChannelAgentTool[]; // 渠道 Agent 工具
};

这里有几个关键设计要点：

  • config 是唯一的必选 Adapter——它提供账户列表、账户解析等基础能力，所有渠道都需要。
  • 其余 15+ Adapter 全部可选——渠道按需实现。一个简单的 webhook 渠道可能只需要 config + gateway + outbound。
  • capabilities 声明渠道能力——告诉 Agent 引擎此渠道是否支持投票、Reaction、媒体、线程等功能。
TypeScript src/channels/plugins/types.core.ts 
export type ChannelCapabilities = {
  chatTypes: Array<ChatType | "thread">;  // "direct" | "group" | "channel" | "thread"
  polls?: boolean;           // 投票
  reactions?: boolean;       // 表情回应
  edit?: boolean;            // 消息编辑
  unsend?: boolean;          // 撤回
  reply?: boolean;           // 引用回复
  effects?: boolean;         // 消息特效
  groupManagement?: boolean; // 群管理
  threads?: boolean;         // 线程/子话题
  media?: boolean;           // 媒体（图片/文件）
  nativeCommands?: boolean;  // 原生命令菜单
  blockStreaming?: boolean;  // 分块流式传输
};
类比

可以把 ChannelPlugin 想象成一个万用充电器接口。USB-C 定义了电力传输和数据传输的标准协议，但不同设备可以只用其中一部分功能——手机用充电 + 数据，耳机只用充电。同理，ChannelPlugin 定义了完整的渠道能力模板，但每个渠道根据自身特性只实现需要的 Adapter。

四层 Adapter 抽象

ChannelPlugin 的 15+ Adapter 可以按职责归纳为四个层次。 这种分层确保了关注点分离——认证逻辑不会混入格式化逻辑，安全策略不会散落在消息解析中。

渠道 Adapter 四层架构
Layer 4: 生命周期与运维
gateway · status · heartbeat · auth
Layer 3: 安全与控制
security · pairing · commands · elevated · groups
Layer 2: 消息处理
outbound · streaming · threading · mentions · actions · messaging
Layer 1: 配置与身份
config · setup · onboarding · configSchema · directory · resolver
层次 Adapter 职责 典型方法
生命周期 gateway 启停账户、QR 登录、登出 startAccount(), stopAccount()
status 探活、审计、快照 probeAccount(), buildAccountSnapshot()
heartbeat 心跳检查、收件人解析 checkReady(), resolveRecipients()
auth 登录认证流程 login()
安全控制 security DM 策略（白名单/配对） resolveDmPolicy()
pairing 设备配对与审批 notifyApproval()
commands 命令权限控制 enforceOwnerForCommands
groups 群组策略（@提及/工具） resolveRequireMention(), resolveToolPolicy()
消息处理 outbound 出站消息发送 sendText(), sendMedia(), sendPoll()
streaming 流式回复配置 blockStreamingCoalesceDefaults
threading 线程/话题路由 resolveReplyToMode(), buildToolContext()
mentions @提及识别与剥离 stripPatterns()

setup 账户创建与配置写入 applyAccountConfig()

以 ChannelOutboundAdapter 为例，它定义了出站消息的完整发送协议：

TypeScript src/channels/plugins/types.adapters.ts 
export type ChannelOutboundAdapter = {
  deliveryMode: "direct" | "gateway" | "hybrid";
  chunker?: ((text: string, limit: number) => string[]) | null;
  chunkerMode?: "text" | "markdown";
  textChunkLimit?: number;
  pollMaxOptions?: number;
  resolveTarget?: (params: {
    cfg?: OpenClawConfig; to?: string;
    allowFrom?: string[]; accountId?: string | null;
    mode?: ChannelOutboundTargetMode;
  }) => { ok: true; to: string } | { ok: false; error: Error };
  sendText?: (ctx: ChannelOutboundContext) => Promise<OutboundDeliveryResult>;
  sendMedia?: (ctx: ChannelOutboundContext) => Promise<OutboundDeliveryResult>;
  sendPoll?: (ctx: ChannelPollContext) => Promise<ChannelPollResult>;
};
关键设计

deliveryMode 决定出站路径："direct" 表示渠道插件直接调用平台 API 发送；"gateway" 表示走 Gateway HTTP 代理；"hybrid" 表示两种模式都支持，按条件自动选择。

注册与发现机制

渠道的注册、发现和生命周期管理分散在几个协作模块中：

Plugin Discovery
plugins/discovery.ts
扫描 workspace、global、bundled 路径
manifest
Plugin Registry
plugins/runtime.ts
全局注册表 + version 缓存
channel[]
Channel Index
channels/plugins/index.ts
排序、去重、按 ID 查找

channels/plugins/index.ts 提供了最终的渠道查询 API。它从 Plugin Registry 拉取所有已注册的 channel 条目，按 CHAT_CHANNEL_ORDER 排序（内置渠道优先），然后去重并缓存：

TypeScript src/channels/plugins/index.ts 
function resolveCachedChannelPlugins(): CachedChannelPlugins {
  const registry = requireActivePluginRegistry();
  const registryVersion = getActivePluginRegistryVersion();
  const cached = cachedChannelPlugins;
  if (cached.registryVersion === registryVersion) {
    return cached;  // 版本未变，直接返回缓存
  }

  const sorted = dedupeChannels(
    registry.channels.map((entry) => entry.plugin)
  ).toSorted((a, b) => {
    const indexA = CHAT_CHANNEL_ORDER.indexOf(a.id as ChatChannelId);
    const indexB = CHAT_CHANNEL_ORDER.indexOf(b.id as ChatChannelId);
    const orderA = a.meta.order ?? (indexA === -1 ? 999 : indexA);
    const orderB = b.meta.order ?? (indexB === -1 ? 999 : indexB);
    return orderA !== orderB ? orderA - orderB : a.id.localeCompare(b.id);
  });
  // ...构建 byId Map 并缓存
}

扩展渠道的注册入口是 api.registerChannel()。以 MS Teams 为例：

TypeScript extensions/msteams/index.ts 
import type { OpenClawPluginApi } from "openclaw/plugin-sdk/msteams";
import { msteamsPlugin } from "./src/channel.js";

const plugin = {
  id: "msteams",
  name: "Microsoft Teams",
  description: "Microsoft Teams channel plugin (Bot Framework)",
  configSchema: emptyPluginConfigSchema(),
  register(api: OpenClawPluginApi) {
    setMSTeamsRuntime(api.runtime);
    api.registerChannel({ plugin: msteamsPlugin });
  },
};

export default plugin;

Plugin Discovery 按优先级扫描四种来源：

优先级 来源 (origin) 说明
0 (最高)config用户配置文件中指定的插件路径
1workspace当前工作区的 extensions/* 目录
2global全局安装的 npm 包
3 (最低)bundledOpenClaw 自带的内置插件
缓存策略

渠道列表使用 registryVersion 做变化检测。每次 Plugin Registry 有变化时 version 递增，查询时如果 version 与缓存一致则直接返回上次结果，避免重复排序和 Map 构建。这是一种无锁的版本化缓存，非常适合单进程 Node.js 架构。

Channel Dock：轻量级共享层

ChannelPlugin 接口很强大，但也很"重"——它可能导入 monitor、web login、puppeteer 等大量依赖。 为了让共享代码路径（回复流、命令权限、沙盒等）能安全地引用渠道行为而不触发这些昂贵导入， OpenClaw 引入了 ChannelDock——一个轻量级的渠道行为子集。

ChannelPlugin（重量级）

  • 完整的 15+ Adapter
  • 可能导入 monitor、login 等模块
  • 只在执行边界（如 Gateway 启动）加载

ChannelDock（轻量级）

  • 仅 capabilities、config、groups、mentions、threading
  • 只引用配置读取器和格式化器
  • 可安全在任何代码路径中导入

消息流转全路径

一条来自 Telegram 的用户消息，从接收到最终回复，经历以下完整路径：

入站消息处理流程
1. Platform
Telegram Bot API
推送 Update
2. Monitor
bot-message.ts
鉴权 + 解析
3. Normalize
normalize/
统一 MsgContext
4. Envelope
inbound-envelope.ts
路由 + 会话
5. Agent Run
auto-reply/
AI 回复

Step 1-2: 平台接入 + Monitor

每个内置渠道有自己的 Monitor 模块（如 src/telegram/bot-message.ts、src/discord/monitor/message-handler.ts、src/slack/monitor/message-handler.ts）。 Monitor 负责接收平台事件、验证权限（allowFrom / DM 策略 / mention gating）、过滤自身消息（防止回环）。

Step 3: Normalize 统一格式

src/channels/plugins/normalize/ 目录下有每个渠道的消息标准化器（telegram.ts, discord.ts, slack.ts, signal.ts, imessage.ts, whatsapp.ts）。它们将平台特定的消息格式转换为统一的 MsgContext，包含 Body, From, To, ChatType, OriginatingChannel, MediaPath 等 20+ 字段。

Step 4: Envelope 路由

InboundEnvelope 将标准化后的消息封装为路由信封，解析出 agentId + sessionKey，确定此消息应该交给哪个 Agent、哪个会话处理。

Step 5: Agent Run

消息通过 auto-reply/ 流水线进入 Agent 引擎。这里将触发 Queue Mode 调度（详见消息处理模式篇），然后执行 AI 推理、工具调用，最终通过 outbound Adapter 将回复发送回原始渠道。

出站路由精确定位

出站回复通过 originatingChannel、originatingTo、originatingAccountId、originatingThreadId 四个字段精确路由回消息来源。这确保了用户在 Telegram Topic A 中提问，回复一定出现在 Topic A；在 Discord Thread B 中提问，回复一定出现在 Thread B。

Extension 扩展开发

OpenClaw 的扩展渠道是独立的 pnpm workspace 包，位于 extensions/ 目录。每个扩展是一个标准的 npm 包，可以独立安装和发布。当前已有 40 个 扩展包（截至 2026 年 3 月）。

channelRuntime (Plugin SDK 2026.2.19+)

ChannelGatewayContext 的 channelRuntime 字段为外部扩展提供 reply（AI 回复调度）、routing（Agent 路由）、session（会话管理）、media（媒体处理）、commands（命令授权）、groups（群组策略）、pairing（配对管理）等高级能力，让外部扩展无需直接导入内部模块。
